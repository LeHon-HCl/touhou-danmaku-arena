# 东方同人弹幕竞技 · Touhou Danmaku Arena

一款**浏览器端**的东方 Project 二次同人**平面弹幕竞技游戏**：在俯视视角的大地图上移动、瞄准、射击，靠走位与预判击败对手，并用角色的专属符卡打出高光时刻。

> ⚠️ **定位声明**
> 本项目为**非商业二次同人创作**，仅在同好群内部分发，不上架任何公开平台、不做推广、不提供公开下载入口。不收费、不内购、不投放广告、不接受赞助。
> 仓库公开仅用于协作开发与版本管理，**不代表授权任何人分发、运营或商用**。

## 这是什么

| | |
|---|---|
| **玩法** | 2–8 人同房实时 PvP，稀疏弹道的"走位对枪"，符卡是唯一的爆发时刻 |
| **题材** | 东方 Project 同人演绎（灵梦、魔理沙等角色与符卡概念） |
| **平台** | PC 浏览器（Chrome / Edge），键鼠操作，60 FPS |
| **规模** | 单房间 2–8 人，同时 1–3 个房间，总在线通常不超过 24 人 |

### 与原作的关键差异

东方原作的乐趣是"在密集弹幕中极限走位"（躲避向），本项目选择的是"**稀疏弹道下的人际对枪**"（预判向）：

- **不追求满屏弹幕**，每一发子弹都有重量，命中靠预判和走位博弈
- 东方元素通过**角色、符卡、美术、Boss 战**承载，而非弹幕密度
- 实际击杀时长目标 8–13 秒（HP 5–10 秒 + 护盾 2–4 秒），节奏接近射击对抗而非弹幕躲避

参考作品：《弓箭手大作战》类 .io 竞技射击（核心参照）+ 东方 Project 系列（题材与美学）。

## 技术栈

| 层 | 选型 | 一句话理由 |
|---|---|---|
| 语言 | **TypeScript** | 同一份战斗逻辑被客户端 / 服务端 / 练习场三处调用，字段名打错要在保存时就报错 |
| 客户端 | **Phaser 4**（4.2.x） | 只用于渲染 / 输入 / 音频 / 资源加载，不承担任何游戏逻辑；省下 Tilemap、相机、图集约 600–800 行基建 |
| 服务端 | **Node + 原生 `ws`** + 自研薄房间层 | 同步模型刻意做得很简单，不需要 Colyseus 那套预测/校正/回溯的框架税 |
| 同步模型 | **状态同步 + 服务端权威**，30Hz 全量快照 | 浏览器浮点与帧率无法保证帧同步所需的严格确定性 |
| 预测边界 | **只预测自身移动** | 稀疏弹道下约 100ms 的出弹延迟不刺眼，预测子弹要额外处理"服务端拒绝这批子弹"，不划算 |
| 构建 | **Vite**（客户端）+ **tsx**（服务端） | 工具链总负担就是这两个，配置文件尽量少 |
| 音频 | **Web Audio API** | 需要 2D 声道偏移与距离衰减，`<audio>` 标签做不到 |

**最硬的一条纪律**：

> `shared/` 里不允许 `import Phaser`，也不允许 `import ws` / `node:*` / `fs` / 任何 DOM API。

因为 `shared/` 要被浏览器（联机客户端）、Node（服务端）、浏览器（离线练习场）三种环境同时执行。破了这条，练习场先崩、服务端再崩，最后只能写两份逻辑——而"两份逻辑不一致"正是本项目最大的技术风险（表现为"显示打中了却没掉血"）。详见 [tech-design.md §8.2](docs/tech-design.md)。

## 目录结构（规划）

```
touhou-danmaku-arena/
├── docs/                  # 四份设计文档
├── shared/                # ⭐ 纯 TS，零框架依赖，三端共用
│   ├── world.ts           # 世界状态数据结构
│   ├── step.ts            # 固定步长推进：输入→移动→碰撞→命中→伤害→复活
│   ├── protocol.ts        # 通信消息类型
│   ├── sim/               # 弹道、命中、护盾与伤害、道具效果
│   └── config/            # 数值配置的 TS 源（唯一真源）
├── assets/                # 素材成品：char/ bullet/ item/ map/ sfx/
├── config/
│   └── game-config.json   # 由 build:config 生成，入库
├── scripts/
│   └── build-config.ts    # shared/config → config/game-config.json
├── client/                # Phaser 4 + Vite
│   └── src/               # main / render / net / input / audio / practice
├── server/                # Node + ws
│   └── src/               # index / room / rooms / log
└── package.json           # 单仓库 workspace
```

三种运行模式共用**同一条** `shared/step.ts`：服务端以 30Hz 权威推进；离线练习场以 30Hz 本地推进；联机客户端的职责只有"预测自己的移动 + 把世界画出来"，它**不推进世界**。

## 开发约定（摘要）

完整条款见 [docs/dev-conventions.md](docs/dev-conventions.md)，这里只列最容易踩的三条。

**1. 双主干分支**

| 分支 | 定位 |
|---|---|
| `main` | 稳定主干，**只接受来自 `dev` 的合并**；打 tag 的就是它能部署的状态 |
| `dev` | 开发主干，日常开发都在这里（**仓库默认分支**） |
| `feat/xxx`、`fix/xxx` | 从 `dev` 拉、做完合回 `dev`，寿命不超过 3 天 |

在 `main` 上做的任何紧急修复，**必须立即合回 `dev`**，否则下次同步会把它覆盖。

**2. 提交信息**

```
<type>: <改了什么，以及为什么>
feat: 加入灵梦的符卡冷却逻辑
fix: 复活点改为离最近敌人最远的点，避免复活即被抓
```

`type` 取 `feat` / `fix` / `docs` / `refactor` / `style` / `chore`。前缀解决"能不能检索"，描述解决"当时为什么这么改"。

**3. 不入库的东西**

`.psd` / `.aseprite` / `.kra` 源文件、`.wav` 母带、`node_modules/`、构建产物、日志——放网盘或群文件。**但 `config/game-config.json` 必须入库**，它是数值的唯一真源。
