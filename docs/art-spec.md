## 0. 本文档的定位

需求文档回答「**要什么样的美术效果**」，本文档回答「**具体怎么画、多大、什么格式、怎么命名**」。

标记沿用需求文档的约定：

| 标记 | 含义               |
| ---- | ------------------ |
| ✅   | 已确认             |
| 💡   | 建议，未确认       |
| ⬜   | 待定，需讨论后填入 |
| ❌   | 明确不做           |

**当前状态**：风格方向、技术规格与资源命名已定（第 1、2、9 章），仍待补的是**素材生产规格**：尺寸（2.3）、地图（第 5 章）、UI 视觉（第 7 章）、音效细节（第 8 章）、授权边界（4.5）。

## 1. 风格总纲 ✅

| 项目             | 内容                                                                                 |
| ---------------- | ------------------------------------------------------------------------------------ |
| 整体风格         | 像素风（pixel art）                                                                  |
| 表现方式         | **场景与镜头为俯视，角色贴图为正面视角**（top-down scene with front-facing sprites） |
| 题材             | 东方 Project 同人，角色为灵梦、魔理沙                                                |
| 选择像素风的理由 | 素材量可控、Web 加载体积小、风格统一、便于后续邀请他人参与绘制                       |
| 颗粒感           | ✅ **中等偏细**（基准：角色 48×48，画面 1280×720）                                   |
| 色板             | ✅ **固定 48 色调色板**                                                              |
| 美术生产方式     | ✅ **AI 生成基础素材 + 人类微调**                                                    |

### 1.1 关于"表现方式"的说明

需求文档定的视角是"平面俯视（top-down），非等距"。这里需要区分两件事：

- **场景是俯视的**：地图从上方看下去，角色在上方视角的场地里移动，墙体有高度感
- **角色贴图是正面视角的**：角色永远面向镜头，转身靠水平翻转

这是一种常见的混合表现（《以撒的结合》是典型例子），玩家不会感到矛盾：场地是俯视的，人是你从侧上方看到的。**不必**也因此**不允许**把角色画成"从头顶看到的头顶"——那是另一种方案，已在 2.1.4 中排除。

### 1.2 颗粒感：中等偏细

定为"中等偏细"，具体含义：

- 角色 48×48 像素，脸部约占 14×14 像素，能画出眼睛与基本表情
- 不是复古 FC 的粗颗粒（16×16 级别，角色只有色块），也不是高清独立游戏的细颗粒（96×96 以上）
- 参照观感：接近 SNES 后期到现代独立像素游戏之间的密度

### 1.3 色板：固定 48 色

**全项目共用一套 48 色调色板，所有素材从中取色，不得使用表外颜色。**

为什么这一条是硬性要求而不是风格偏好：

1. **AI 出图的配色是随机的**。同一个角色出十张图，红色会有十种。不锁色板，灵梦的红衣与地图的砖红很容易撞在一起，直接破坏需求 3.1 的敌我辨识（这是需求级硬约束，不可妥协）。
2. **统一风格的最低成本手段**。像素风的"整体感"主要来自色板一致，而不是画风细节。
3. **素材量化的前提**。后处理流程（见 2.5）的"调色板量化"一步，必须有一份确定的色板作为目标。

⬜ 48 色的具体构成待定。需要分配的是：角色配色（每角色约 8–12 色）、地表与掩体、弹幕（需高对比）、特效、UI。

## 2. 技术规格（已定）

本章五项属于"定错了要返工全部素材"的决定，**已全部确定**。

### 2.1 角色朝向：正面固定 + 水平翻转 ✅

**方案：每个角色只绘制一个正面朝向，左右方向由程序水平翻转（`setFlipX`）得到。**

三个理由，按重要程度排列：

**一、它把 AI 生成的最大弱点绕开了。**

AI 出图最不稳定的地方是"一致性"：同一个角色画 8 个方向、每个方向 4 帧，会得到 8 个长得不太一样的人（比例、配色、服饰细节都会漂移）。人类微调要把它们逐个修到统一，工作量远超重画。

只画一个朝向，一致性问题从根上消失。

**二、素材量降到十分之一量级。**

详见 4.2 的动画表：每角色 4–5 张原图，两个角色约 9 张。

**三、翻转本身有正收益，不只是省事。**

左右移动时的镜像切换提供了一个**状态突变**，玩家读作"转身了"。若角色完全对称，左右移动只表现为位置平移，观感上会变成"在飘"。因此**不对称细节是被鼓励的**，规范见 2.1.2。

#### 2.1.1 朝向与瞄准解绑（重要）

**角色朝向 ≠ 子弹方向。** 这是设计选择，不是 bug，实现与测试时都必须清楚。

| 项目                 | 行为                                             |
| -------------------- | ------------------------------------------------ |
| 子弹、符卡的飞行方向 | 指向**鼠标位置**                                 |
| 角色贴图的朝向       | **最近一次水平移动的方向**（左 or 右），仅此二态 |
| 向上或向下瞄准时     | 角色贴图不变化，仍是正面                         |

为什么可以接受：本项目是稀疏弹道竞技，玩家要判断的是"子弹从哪来、会飞向哪"，而"角色面朝哪"并不承载战术信息。角色贴图只承担两件事——**这是谁**、**我在往哪个方向走**。

如果将来觉得违和，补救手段是加一个"脚下朝向箭头"或"枪口指向指示器"，属于程序侧增强，不需要重画素材。⬜ 是否加待实测。

#### 2.1.2 不对称设计规范 ✅

不对称分两档，只有第一档允许：

| 类型             | 判定              | 例子                                                                     |
| ---------------- | ----------------- | ------------------------------------------------------------------------ |
| **细节级不对称** | ✅ **允许且鼓励** | 灵梦的蝴蝶结偏向一侧、袖子长度；魔理沙帽子的星星位置、围裙系带、单侧发束 |
| **结构级不对称** | ❌ **禁止**       | 左右两半颜色不同、单边披风、半边身体被遮挡、轮廓强偏左右                 |

区别在于翻转时的观感：细节级不对称翻转后，"这个人转身了"；结构级不对称翻转后，"换成了另一个人"，甚至会被误读为敌我阵营变化。

**翻转不做过渡帧，瞬间切换。** 过渡会削弱转向的冲击感，而且正面固定方案里没有侧面帧可以拿来做中间帧。

#### 2.1.3 描边必须实时生成，不得烘焙进 sprite ✅

敌方红色荧光描边（需求 3.1）**必须由渲染器实时生成**（Phaser 4 的 Filters / Glow），不能预先画进 sprite 图像。

这条不是技术偏好，它直接决定素材量：

| 做法          | 隐身道具的实现成本                                  | 翻转                 |
| ------------- | --------------------------------------------------- | -------------------- |
| 烘焙进 sprite | 每个状态要做"有描边版 + 无描边版"两份，素材**翻倍** | 描边随图翻转，无问题 |
| **实时生成**  | 代码里关掉描边即可，**素材量不变**                  | 描边自动跟随翻转     |

需求附录 A 的隐身效果 = **移除红色描边 + 小地图标记消失**。若描边烘焙，7 张原图会变成 14 张，而且运行时还要处理两种贴图的切换。

#### 2.1.4 已排除方案（留档，避免重复讨论）

| 方案                        | 为什么排除                                                                                                                                                                    |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **8 方向 sprite**           | 像素风的标准做法，转向最精确，但素材量约 80–256 帧（按状态区分后）。在"AI 生成 + 人类微调"的分工下，帧间一致性无法保证，微调成本超过收益                                      |
| **4 方向 sprite**           | 折中方案，素材量减半，但斜向瞄准时朝向有 45° 跳变感。且一致性问题和 8 向同等严重                                                                                              |
| **整体旋转**                | ❌ **像素网格与任意角度在数学上不兼容**。旋转后每个像素落在小数坐标，最近邻采样会丢像素与重复像素，边缘出现不规则缺口，且每旋转 1° 缺口位置都在变，观感是"抖动"。45° 附近最糟 |
| **身体固定 + 独立武器旋转** | 引入拆件与层级逻辑，48×48 的尺寸下武器零件太小，收益低于成本                                                                                                                  |

补充：**倾斜与缩放同样会破坏像素网格**，与旋转是同一类问题。因此"移动时身体前倾""呼吸缩放"这类常见手法在本项目**一律不能用**，移动感的实现手段见 4.3。

### 2.2 逻辑分辨率与缩放 ✅

| 项目         | 决定                                                   |
| ------------ | ------------------------------------------------------ |
| 逻辑分辨率   | **1280×720**（16:9；像素坐标与素材尺寸仍以世界单位计） |
| 放缩方式     | **整数倍放大**到窗口（2× / 3× / 4×）                   |
| 非整数倍窗口 | **保持黑边，不拉伸**                                   |

为什么 1280×720：基于原 640×360 逻辑画布翻倍，以容纳更大字号的文字与 HUD；角色和地图仍按原世界单位绘制，因此相机每屏能看到更多地图。整数倍缩放仍保持屏幕像素方正，不改变 48×48 角色素材本身。

为什么非整数倍时选黑边而不拉伸：拉伸会让像素块变成宽高不等的长方形，像素风立刻"糊掉"，比两侧有黑边难看得多。**宁可留边，不可破坏像素形状。**

分辨率提高后视野随之扩大，镜头继续以玩家为中心跟随并受地图边界约束。若实测发现玩家过小或信息过载，再单独调整相机 zoom / deadzone；不通过改变世界坐标来影响碰撞与战斗数值。

⬜ 待定：是否需要提供 1.5× 之类的折中缩放档（部分像素游戏会在窄窗口下允许轻微模糊以避免黑边过宽）。

### 2.3 sprite 尺寸

| 资源      | 尺寸      | 状态                |
| --------- | --------- | ------------------- |
| 角色      | **48×48** | ✅                  |
| 子弹      | **12×12** | ✅ 已按占位素材定档 |
| 道具图标  | **24×24** | ✅ 已按占位素材定档 |
| 地图 tile | **32×32** | ✅ 已按占位素材定档 |

> 这几个尺寸就是 `assets/images/` 下文件的实际要求，逐文件名对照表见 [assets/README.md](../assets/README.md)。
> 程序启动时会校验尺寸，不符只告警、不阻断（方便临时试素材），但正式交付必须按表来。

**48×48 的构图要求**：

- 角色本体占据约 **40×44** 像素，四周至少留 **2 像素空白**
- 留白不是为了好看，是**给描边留位置**：描边在 sprite 外侧生成，如果角色贴边，描边会被 sprite 边界裁掉，四个方向都会缺一截
- 脚下不需要画投影，阴影由程序绘制（见 4.3），因为阴影要随移动滞后，画死在图里就动不了

### 2.4 像素对齐策略 ✅

| 项目               | 决定                                                     |
| ------------------ | -------------------------------------------------------- |
| 是否强制对齐像素格 | **不对齐，保留亚像素位置**                               |
| 适用范围           | **整个渲染层统一**：角色、子弹、粒子、相机跟随、地图滚动 |

不对齐像素意味着渲染时保留小数坐标，运动更平滑。代价是**运动时像素边缘会有亚像素级闪烁**（放大 3 倍后幅度约 1 个屏幕像素，相对 48px 角色占 0.7%），静止时完全清晰。

**为什么必须整个渲染层统一**：若角色不对齐、相机却按整数像素跳动，角色在画面中的相对位置会一顿一顿，比两者都对齐更难看。不存在"只让角色不对齐"这种选项。

实现时注意：Phaser 的像素取整类配置（v3 为 `roundPixels`，v4 的确切配置名在实现时确认）需要**显式关闭**，且相机跟随不能对目标位置做整数取整。

### 2.5 素材后处理流程 ✅

AI 生成的原图不能直接使用。**AI 出的是"假像素"**：分辨率不规整、边缘带半透明抗锯齿、像素块大小不一致。直接缩放会得到"低分辨率照片"而不是像素画，而且描边会沿着毛刺生成一圈脏光。

标准流程：

| 步骤 | 做什么                  | 为什么                                                                                         |
| ---- | ----------------------- | ---------------------------------------------------------------------------------------------- |
| 1    | 裁出角色，去掉背景      | AI 出图通常带背景                                                                              |
| 2    | 缩放到目标尺寸（48×48） | 使用最近邻（Nearest）采样，**关闭所有平滑/双线性**                                             |
| 3    | 调色板量化              | 把颜色对齐到项目的 48 色板，消除 AI 的随机配色                                                 |
| 4    | **alpha 二值化**        | 半透明边缘必须二值化：要么完全透明，要么完全不透明。残留的半透明像素会让描边变成脏边（见 3.1） |
| 5    | 边缘检查                | 确认四周留白 ≥2px，角色不贴边                                                                  |
| 6    | 人工修整                | 修清楚眼睛、轮廓和辨识特征                                                                     |

**诚实说明**：第 6 步没有自动化的办法。48×48 的像素级修整——让眼睛像眼睛、让轮廓干净——只能人眼看着改。这是"人类微调"的主要开销，按每张 10–20 分钟估算。

## 3. 可读性约束（需求级，不可妥协）✅

### 3.1 敌我辨识

- 敌方角色与敌方弹幕的**外轮廓加红色荧光描边**
- 描边不得遮挡本体，只包在外侧
- 敌弹描边要考虑粗细，不能因为描边导致弹道更难辨认
- 团队战中队友不加敌色描边
- **描边由渲染器实时生成，不得烘焙进 sprite**（理由见 2.1.3）
- ⭐ **素材边缘的 alpha 必须二值化**：这是描边能否干净的前提。半透明边缘会让描边沿着半透明像素生成，出现一圈发毛的脏光，在深色背景上尤其明显

⬜ 待定：描边颜色是否可替换（色弱考虑，如红/蓝可选）
⬜ 待定：队友是否需要专属描边色（淡蓝）

### 3.2 子弹的可辨识性 ✅

稀疏弹道下，玩家需要立刻看清"哪颗子弹是冲我来的"。因此：

- 子弹必须在任何地图背景上都**足够显眼**（对比度要求）
- ⬜ 待定：不同角色的子弹是否用不同颜色区分（东方传统里颜色是信息，本项目要不要继承）

### 3.3 特效不得遮挡判定

💡 符卡特效、命中特效的视觉表现不能盖住实际判定区域，否则玩家会"看不见子弹但被打中"。

### 4.2 动画状态与素材清单 ✅

**关键原则：只有必须"长得不一样"的状态才需要 AI 出图，其余用程序处理。**

| 状态       | 素材来源                        | 帧数 | 说明                       |

| 待机       | **AI 出图 1 张**                | 1    | 基准姿势，其他状态的参照   |
| 移动       | **AI 出图 +1 张**（同姿势改腿） | 2    | 腿部交替，每约 0.15 秒切换 |
| 射击       | 复用待机图                      | 0    | 枪口闪光由程序叠加         |
| 受击       | 复用待机图                      | 0    | 闪白着色由程序处理，不换图 |
| 阵亡       | **AI 出图 1 张**                | 1    | 倒地或变灰                 |
| 释放符卡   | **AI 出图 1 张**                | 1    | 举手/蓄力姿势              |
| 护盾存在时 | 复用待机图                      | 0    | 叠加光效图层，程序绘制     |

**每角色 4 张原图，两个角色共 8 张。** 按每张 10–20 分钟微调，总计约 2–3 小时。

⬜ 待定：

- 是否需要"出生/复活"动画（可用程序特效代替）
- 护盾光效的具体形式（外圈光环 / 全身罩色 / 边缘描边变色）

### 4.3 移动表现 ✅

因为"倾斜与缩放都不能用"（见 2.1.4），移动感只能靠位移类的表现。**已定基础三项**：

| 手段         | 做法                                        | 承担的作用                                                            |
| ------------ | ------------------------------------------- | --------------------------------------------------------------------- |
| 水平翻转     | 左右移动时镜像                              | 转向反馈，靠 2.1.2 的不对称细节承载                                   |
| **2 帧走路** | 腿部交替，每约 0.15 秒切换                  | **主力**。唯一能让"走"真正成立的手段                                  |
| 步频起伏     | 移动时整体上下偏移 1 逻辑像素，与走路帧同步 | 节奏感。因不对齐像素（2.4），表现为柔和的亚像素位移，**不能单独依赖** |

以下两项列为**后续可选**，MVP 不做：

| 手段     | 说明                               | 为什么暂缓                               |
| -------- | ---------------------------------- | ---------------------------------------- |
| 脚下阴影 | 椭圆阴影独立于角色，移动时略微滞后 | 增加"重心"感，但需调参                   |
| 移动扬尘 | 脚下小碎步特效                     | 8 人混战时扬尘会干扰弹幕可读性，需先验证 |

⬜ 待定：走路帧的切换是否随移速变化（移速强化道具生效时步频加快）。💡 建议**不随移速变化**，固定频率，否则增益期间动作会显得抽搐。

### 4.4 AI 出图规范 ✅

给 AI 的提示词与出图要求，目的是**减少后处理工作量**：

| 项目   | 要求                                           | 理由                             |
| ------ | ---------------------------------------------- | -------------------------------- |
| 姿态   | 正面站姿，身体正对镜头                         | 与 2.1 的翻转方案一致            |
| 对称性 | **细节可不对称（鼓励）**，但不允许结构级不对称 | 见 2.1.2                         |
| 背景   | 纯色、与角色主色高对比                         | 便于裁切                         |
| 边缘   | 硬边，无抗锯齿、无羽化、半透明描边             | 见 2.5 第 4 步                   |
| 投影   | **不画**                                       | 阴影由程序绘制（4.3）            |
| 留白   | 角色四周留出画面 10% 以上空白                  | 便于裁切与缩放，且要给描边留位置 |
| 画布   | 正方形，建议 512×512 或以上                    | 尺寸过小时 AI 会把"像素块"画得糊 |
| 色彩   | 提示词中尽量描述"限制配色、平涂、无渐变"       | 减少后处理量化时的工作量         |
| 内容   | 东方角色同人演绎，须为自行绘制或合法授权的形象 | 见 4.5                           |

**风险提示**：AI 生成的"像素风"通常只是**视觉上像像素**，实际像素块大小不一致、网格不规整。不要指望通过提示词得到可用于 48×48 的成品，**后处理与人工修整是必经步骤**。

### 4.5 原创性要求

- 东方角色为同人演绎，需保证是**自行绘制或合法授权的同人形象**，不得直接使用原作或他人的同人素材
- ⬜ 待定：AI 生成素材的授权边界（需确认所用工具的服务条款是否允许生成物用于同人作品），以及是否需要在项目内登记每张图的生成来源与工具
- ⬜ 待定：是否需要约定角色立绘（用于选人界面），还是仅需游戏内 sprite

## 9. 资源交付与命名 ✅（规则已归位）

**命名规则已定案，唯一权威来源是 [dev-conventions.md](./dev-conventions.md) 第 7 章**，本文档不重复维护一份。

| 项目                         | 结论                                                                | 权威位置                                |
| ---------------------------- | ------------------------------------------------------------------- | --------------------------------------- |
| 文件命名                     | 全小写 ASCII，`主体_状态_序号`，两位序号（`reimu_idle_00.png`）     | dev-conventions 7.2                     |
| 目录组织                     | 按**介质**分目录：`assets/images/`（图片）、`assets/audio/`（音频） | 本表（v0.4 修订，见下）                 |
| 是否带尺寸前缀               | ❌ 不带。尺寸写在本文 2.3 的规格表里                                | dev-conventions 7.2                     |
| 图集打包                     | ❌ MVP 不打包；地图 tileset 是唯一例外                              | dev-conventions 7.3 / tech-design 7.2.2 |
| 美术源文件（`.aseprite` 等） | ❌ 不入库                                                           | dev-conventions 3.3                     |
| AI 生成的原图                | ❌ 不入库（体积大、可重生成）                                       | dev-conventions 7.4                     |
| AI 生成用的提示词            | ✅ **必须入库**，与素材同目录的 `_prompts.md`                       | dev-conventions 7.4                     |

**本文档仍然负责的部分**：素材**清单本身**——有几个角色、每个角色几张图、每种道具一个图标、音效多少个。文件名的"主体/状态"段就取自这份清单，清单增加一项，命名随之增加一条。所以第 4.2 节的动画表和第 6 节的音效清单一旦扩展，命名规范不需要改，只需按规则加文件。

> **v0.4 修订：目录改为按介质分**。原计划按类型分（`assets/char/`、`assets/bullet/`、`assets/sfx/`…），
> 实际落地时改成 `assets/images/` 与 `assets/audio/` 两个平铺目录：
> 改素材的人不用先判断"这个算 char 还是算 bullet"，放进去就生效。
> **每个文件的准确文件名、尺寸、时长见 [assets/README.md](../assets/README.md)**，那份清单是程序实际读取的路径，优先级高于本章。
