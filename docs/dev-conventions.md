## 1. 语言与命名 ✅

**语言已定案：TypeScript**（见 [tech-design.md](./tech-design.md) 7.1）。因此命名风格不再需要"与所选语言一致"这种含糊表述，直接按 TS 惯例写死。

| 条目 | 规则 |
|---|---|
| 代码标识符语言 | ✅ **英文**（变量、函数、类名、配置字段名） |
| 注释语言 | ✅ **中文** |
| 提交信息语言 | ✅ **中文** |
| 文档语言 | ✅ **中文** |
| 命名风格 | ✅ 变量/函数 `camelCase`；类型/接口/枚举 `PascalCase`；常量 `UPPER_SNAKE_CASE`；文件名 `kebab-case`；布尔值以 `is`/`has`/`can` 开头 |

**为什么标识符用英文而其余用中文**：

- 标识符用英文，是为了不出现拼音命名（`shanghai` 这种既不好读也搜不到），也避开中文名在编码、报错信息、第三方库接口中的各种边角问题
- 注释、提交、文档用中文，是因为**没有外部协作者**，中文表达更准确、读得更快。这不是风格问题，是阅读成本问题

**一个例外**：Git 分支名可以用中文（`feat/符卡冷却`），因为它只出现在本地与合并记录里，不参与代码运行。

✅ 配置表字段名同属这一条规则，一律**全小写驼峰**（`maxHp`、`fireInterval`），详见 6.6。

## 3. Git 流程 ✅

### 3.1 双主干：`main` 稳定版 + `dev` 开发版

```
main:  ─────●─────────────●──────────────●───▶  只有"能完整打完一局"的版本
            ▲             ▲              ▲
            │ 合并+打tag    │              │
dev:   ─────┴──●──●──●─────┴──●──●──●─────┴──▶  日常开发都在这
              ╲    ╱         ╲    ╱
               ●──●           ●──●              功能分支（从 dev 拉，做完合回 dev）
```

| 分支 | 定位 | 谁能提交 |
|---|---|---|
| `main` | **稳定主干**。不追求功能完整，追求**少错误、随时能玩**。部署上线的就是这个 | 只接受来自 `dev` 的合并，或紧急修复 |
| `dev` | **开发主干**。日常开发都在这里，允许暂时不完整 | 所有人，通过功能分支合入 |
| `feat/xxx`、`fix/xxx` | 短期功能分支，从 `dev` 拉，做完合回 `dev` | 各自开发者 |

**六条规则**（第 3 条是这条流程唯一的致命点，务必遵守）：

1. 日常开发一律在 `dev` 上，**不在 `main` 上开发**
2. `main` 只接受两种改动：来自 `dev` 的合并、紧急修复
3. ⭐ **任何在 `main` 上做的修复，必须立即合回 `dev`**。否则下次 `dev` → `main` 同步会把它覆盖，修好的 bug 复活，而且极难查
4. **把 `dev` 设为仓库默认分支**。否则新人 `clone` 下来默认站在 `main` 上改代码，提交后没人看得到
5. 同步到 `main` 的条件：`dev` 上**能完整打完一局、无已知阻塞性 bug**。满足就打 tag（`v0.1`、`v0.2`…）再合并
6. 部署只部署 `main` 上的带 tag 提交，不部署 `dev`

💡 为什么不用更简单的单主干：单主干时"合进 main"就等于"我验证过了"，任何人都可能把半成品推进主干；双主干给半成品一条天然的隔离带，`main` 永远是可以直接开一局的状态。代价是要守住上面第 3 条。

### 3.2 功能分支

- 命名：`feat/符卡冷却`、`fix/复活点选择`，**可以用中文**（只出现在本地与合并记录里）
- **不强制 PR 评审**。评审是一个人形闸门，团队人员流动时他不在一线就会卡死所有人，不适合本项目
- **分支寿命不超过 3 天**。超过 3 天未合并的，问一句"还做吗"，不做就删。长期分支是巨型冲突的唯一来源
- **合并前自己跑一遍能启动**。没有评审者，这条就是唯一的闸门，必须自己守

### 3.3 大文件与美术源文件 ✅

| 文件类型 | 是否入库 | 说明 |
|---|---|---|
| 导出成品（`.png`、图集、`.ogg`） | ✅ 入库 | 游戏运行需要，且体积可控 |
| 美术源文件（`.aseprite`、`.psd`、`.kra`） | ❌ **不入库** | 放网盘或群文件 |
| 音频源文件（工程文件、`.wav` 母带） | ❌ 不入库 | 同上 |

**理由**：Git 会把每个版本的完整文件都存进历史。一个 20 MB 的源文件改十次，仓库就多 200 MB，而且**永远删不掉**（删了也只是新增一个删除记录，历史里仍然存在，后来者 clone 仍要下载）。

**直接后果**：`.gitignore` 需包含 `*.aseprite`、`*.psd`、`*.kra` 及 `node_modules/`、构建产物目录。

#### 3.3.1 忽略清单 ✅

```gitignore
# 依赖与构建产物
node_modules/
dist/
build/
.vite/
coverage/

# 美术/音频源文件（见上表）
# 注意：.gitignore 不支持行尾注释，# 必须单独成行
*.aseprite
*.psd
*.kra
*.wav

# 环境与本地配置
.env
.env.*
!.env.example

# 日志（服务端对局日志见需求 10.7，同样不入库）
logs/
*.log

# 系统与编辑器（团队共享的 .vscode 配置可后续用 ! 例外放开）
.DS_Store
Thumbs.db
.idea/
.vscode/
```

配套 `.gitattributes`（两行即可，作用是避免 Windows / macOS 提交时换行符互相污染 diff）：

```gitattributes
* text=auto eol=lf
*.png binary
*.ogg binary
```

⚠️ **`config/` 绝对不能进忽略清单**。配置是唯一真源且必须入库（见 6.5），把它 ignore 掉等于让每个人手里有一份不同的数值。

## 4. 提交信息格式 ✅

**采用完整版约定式提交，六类前缀。**

```
<type>: <改了什么>

feat: 加入灵梦的符卡冷却逻辑
fix: 修复复活点选择时未选到离敌人最远的点
docs: 更新需求文档 4.2 节
refactor: 抽出伤害结算为独立模块
style: 统一 shared/ 内的缩进
chore: 升级 Vite 到 5.4
```

| type | 含义 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修 bug |
| `docs` | 文档 |
| `refactor` | 重构（不改变行为） |
| `style` | 格式调整（不影响逻辑） |
| `chore` | 杂项（依赖、构建、配置） |

**额外要求（比前缀更重要）**：描述要写**为什么**，不只写改了什么。

| ❌ 差 | ✅ 好 |
|---|---|
| `fix: 改复活点` | `fix: 复活点改为离最近敌人最远的点，避免复活即被抓` |
| `feat: 加道具` | `feat: 加入护盾发生器，拾取后强制进入回盾状态（无视脱战条件）` |
| `refactor: 改代码` | `refactor: 把伤害结算从 step.ts 抽出，便于单测` |

理由：前缀解决"能不能检索"，描述解决"当时为什么这么改"。三个月后你回看时，后者比前者值钱得多，而它不需要任何记忆成本。

## 5. 代码质量 ✅

### 5.1 工具 ✅

| 工具 | 职责 | 状态 |
|---|---|---|
| **Prettier** | 自动排版（缩进、引号、换行）。消除格式争论，让 diff 只包含真实改动 | ✅ 采用 |
| **ESLint** | 找潜在错误（未使用变量、误用 `==`），并**执行 `shared/` 依赖禁令** | ✅ 采用 |
| **pre-commit 钩子** | 提交前自动跑一次格式化，格式不合规的提交进不了历史 | ✅ 采用 |
| 类型严格度 | `strict: true` | ✅ |

**为什么 ESLint 是必需的，不只是"风格工具"**：第 2 章那条"`shared/` 不允许依赖框架"的硬纪律，**没有 ESLint 就只是一句口号**。规则如下：

```js
// shared/ 的 ESLint 限制（示意）
'no-restricted-imports': ['error', {
  patterns: [
    { group: ['phaser', 'ws', 'node:*', 'fs', 'path'], message: 'shared/ 必须三端通用，禁止依赖框架与 Node API' },
    { group: ['**/client/**', '**/server/**'], message: 'shared/ 不能反向依赖 client 或 server' },
  ],
}]
```

配合 tech-design 8.2 的 `lib: ES2022`（拦 `window`、`document` 这类全局 API），两道保险分别管 import 路径和全局变量。

### 5.2 测试范围 ✅

**只测纯数值逻辑，其余不强制。**

| 必须有测试 | 不需要测试 |
|---|---|
| 伤害结算（含护盾硬化的溢出、破盾后的 HP 扣除） | 渲染、美术表现 |
| 护盾机制（脱战回复、上限提升与截断） | 网络同步、重连 |
| 复活点选择（离最近敌人最远） | UI、输入处理 |
| 道具效果叠加与到期 | 音效播放 |
| 符卡冷却与释放条件 | 房间流程 |

**为什么必须有**：这些是**纯数字逻辑且互相牵连**。你每次调平衡都会动它们，而改错的后果不是报错，是**数值悄悄算错**——可能一周后才有人说"怎么打不死人了"。测试能把这个发现周期从一周压到几秒。

举个具体的用例（就是需求附录 A.3 讨论过的那个坑）：

```
护盾剩 5，受到 20 点伤害，处于"防御强化"期间（1 点护盾当 2 点用）
期望：护盾清零，HP 扣 10
错误实现会得到：扣 2.5 护盾 + 17.5 HP —— 盾没破血掉一大半，玩家会认为这是负面道具
```

这条如果写成测试，任何人改坏它都会当场红。

**为什么其余不强制**：渲染、网络这类问题的表现是"看得出来"，靠实际操作验证比写测试快。这个项目人少，测试范围宜窄而准，不宜铺开——铺开的测试没人维护，最后全部跳过。

### 5.3 测试运行工具：Vitest ✅

| 项目 | 结论 |
|---|---|
| 工具 | **Vitest** |
| 安装 | `npm i -D vitest`，在根 `package.json` 加 `"test": "vitest run"`、`"test:watch": "vitest"` |
| 配置 | **不需要 `vitest.config.ts`**。默认就能跑，这个项目没有 DOM、没有别名、没有覆盖率门槛 |
| 测试文件位置 | 与被测文件同目录，命名 `xxx.test.ts`（如 `shared/sim/damage.test.ts`） |
| 运行时机 | 改完数值或改完结算逻辑后手动跑一次；**不接 CI、不做 pre-commit 强制** |
| 不测什么 | 渲染、网络、房间流程（见 5.2 的右列） |

**为什么是它**：与 Vite 同生态，共用同一套 TS 解析，不额外引入 Babel / ts-node / jest 的 transform 配置。本项目只测 `shared/` 里的纯函数，连 `environment: 'jsdom'` 都不需要，装完直接能写第一个用例。

**为什么不接 CI**：单人/小团队的项目，CI 的收益是"防止别人合入破坏测试"，而这个项目没有评审环节（3.2），测试的价值主要在**自己改数值时当场发现算错**。手动跑一条命令就够，上 CI 只是多一份要维护的配置。

## 6. 配置表规范 ✅

需求要求道具与角色"数据驱动、可扩展"（需求 6.4），因此配置表是核心资产。本章的每一条都是为了让"改一个数字"变成不需要编程知识的事。

### 6.1 格式：TypeScript 模块 ✅

配置写在 `shared/config/` 下的 TS 文件里，直接导出带类型的对象：

```ts
export const characters = {
  marisa: {
    /** 单发伤害。建议范围 6–12；越高越接近两发破盾 */
    damage: 8,
    /** 射击间隔（毫秒）。60000 ÷ 该值 = 每分钟发数；当前值 = 400 发/分 */
    fireInterval: 150,
  },
} satisfies CharacterConfig;
```

| 好处 | 说明 |
|---|---|
| 写错当场报红 | 字段名拼错、数字写成字符串、漏字段，保存时编辑器就标红，不用等开一局才发现 |
| 可以写中文注释 | JSON 不支持注释，而注释正是"改数值不需要问人"的关键 |
| 有补全 | 输入 `marisa.` 就列出有哪些字段，不需要记 |

**联机下发**：构建时自动导出为 JSON 交给服务端（需求 10.5 的"服务端为真源"）。这一步已串进开发与服务端启动脚本，日常改数值不需要单独记命令。完整管道见 [tech-design.md](./tech-design.md) 7.2.1，生效流程见本文 6.6.4。

### 6.2 单位约定 ✅

| 类别 | 单位 | 写法示例 | 为什么 |
|---|---|---|---|
| 时间 | **毫秒（ms）** | `fireInterval: 150` | 全是整数，不出现 `0.0333` 这种多位小数；与 30Hz 逻辑帧（33.33ms）天然对齐 |
| 距离 | **像素（px）** | `radius: 12` | 与渲染坐标一致，无需换算 |
| 速度 | **像素/秒（px/s）** | `bulletSpeed: 600` | 与帧率解耦。若写"每帧多少像素"，改帧率就要全表重算 |
| 角度 | **度（°）**，代码内部转弧度 | `spread: 15` | 配置里写人类能理解的值，转换由代码做 |

### 6.3 注释要求（强制）✅

**每个字段必须带中文说明 + 建议范围**，无例外。

```ts
/** 单发伤害。建议范围 6–12；越高越接近两发破盾 */   ✅
damage: 8,                                          ✅

damage: 8,   // 伤害                                  ❌ 缺范围，等于没写
```

理由：数值调整是高频操作，如果每次都要问"这个字段是什么意思、能调到多少"，配置驱动就失去意义了。写一次注释，省掉之后几十次询问。

### 6.4 维护分工 ✅

| 操作 | 谁做 | 频率 |
|---|---|---|
| **改数字**（调平衡：伤害、血量、冷却、移速、道具时长） | **项目负责人自己做** | 高 |
| **改结构**（新增字段、新增角色、新增道具效果类型） | 程序 | 低 |

改数字是高频、低风险（有 TS 类型兜底，写错当场报红），所以不应依赖某个人在线。改结构会牵连校验、渲染、效果处理器，必须由程序做。

### 6.5 配置必须入库 ✅

**改数值 = 改本地配置 + 提交 + 部署。禁止直接改服务器上的配置文件。**

原因：联机时以服务端配置为准，如果只在服务器上改，下次任何人部署新版本时**你的调整会被覆盖**，而且没人记得改过什么。这类"数值莫名回退"在多人项目里非常常见，排查起来极其费时。

提交信息按第 4 章，例如：

```
fix: 魔理沙单发伤害 8→6（对拼太强，盾两发就破）
chore: 移速强化持续时间 10s→8s（实测过长）
```

### 6.6 配置的版本、校验与生效 ✅

#### 6.6.1 字段命名：全小写驼峰

| 写法 | 结论 | 例子 |
|---|---|---|
| 全小写驼峰 | ✅ **采用** | `maxHp`、`fireInterval`、`shieldRegenDelay`、`isPiercing` |
| 全大写（`HP`、`MAXHP`） | ❌ | 与 §1 的 `UPPER_SNAKE_CASE`（常量）规则冲突，读代码时会误以为是编译期常量 |
| 下划线（`max_hp`） | ❌ | TS 生态里少见，且与 `shared/` 内的变量命名不一致 |

**单位默认不写进字段名**：用 `fireInterval` 而不是 `fireIntervalMs`。因为 6.2 已经把单位全局定死（时间一律毫秒、距离一律像素），每个字段都带后缀是重复编码。**唯一的例外是偏离全局约定的字段**——比如某个字段确实要用秒，那必须写成 `xxxSeconds` 并在注释里说明为什么偏离。

#### 6.6.2 配置版本号：构建时内容 hash

| 项目 | 结论 |
|---|---|
| 生成方式 | `npm run build:config` 时对导出的 JSON 内容算一次 hash（取前 8 位），写进 JSON 顶层的 `version` 字段 |
| 是否手写 | ❌ **不手写 semver**。手写版本号一定会出现"改了数值忘了改版本号"，hash 不会 |
| 用途 | **仅用于日志排查**：服务端启动日志与每局对局日志各记一条 `configVersion`，事后能回答"这局为什么数值不一样" |
| 是否用于拦截 | ❌ **不做客户端比对拦截**。联机时服务端下发完整配置（需求 10.5），客户端本来就直接用服务端的值，不存在"两端各算一套" |

**为什么版本号不做拦截**：需求 10.5 定的是"服务端下发为准、客户端内置值仅作离线兜底"。既然联机时全部数值都来自下发，客户端内置值新旧不影响判定，只是少一次刷新。加一道"版本不符禁止加入"的闸门，收益为零，却会在部署顺序出错时把所有人挡在门外。

#### 6.6.3 运行时校验：只查三项，不引 schema

| 检查项 | 做法 |
|---|---|
| 文件存在 | `fs.existsSync` 失败则**拒绝启动**并打印期望路径 |
| 可解析 | `JSON.parse` 失败则拒绝启动，打印出错位置 |
| 版本字段存在 | `version` 缺失则拒绝启动（说明构建脚本没跑或跑错了） |

**不引入 zod / ajv 等 schema 校验器**，理由：

1. JSON 是**我们自己的构建脚本从 TS 模块产出的**，字段完整性、类型正确性在编译期已由 `satisfies` 保证（6.1），再写一份 schema 等于维护第二份字段清单
2. 那份清单会和 TS 类型逐渐漂移，**正是风险 R1（两处各写一份）的同型问题**，只是从"客户端/服务端"换成了"类型/schema"
3. 校验器拦不住的恰恰是最常见的问题——"数值填得离谱但不违反类型"（伤害写成 800）。这个只能靠 6.3 的"建议范围"注释 + 实测发现

**这套方案的适用边界**：配置只从**仓库内的构建产物**加载。如果将来改成"运维可直接改服务器上的 JSON 热更新"，边界就破了，那时必须补 schema 校验。**这条边界要写进部署文档。**

#### 6.6.4 数值生效流程 ✅

改一个数字的完整路径：

```
① 改 shared/config/*.ts 里的数值（改完当场有类型检查）
        ↓
② npm run build:config      生成 config/game-config.json + version hash
        ↓
③ git commit（提交信息按第 4 章写"为什么改"）
        ↓
④ 部署（把新 JSON 与代码一起送到服务器，见 tech-design 第 6 章）
        ↓
⑤ 重启服务端进程            配置在进程启动时读入
```

**关键一点：前端不需要重新构建**。数值走服务端下发（需求 10.5），所以第 ④ 步只影响服务端产物，改数字时前端静态文件不用动。

⬜ 第 ⑤ 步的具体命令取决于部署方式（`systemd restart` / `pm2 restart` / `docker restart`），随 tech-design 第 6 章确定后补入。**在此之前，这条流程本身已经确定，缺的只是一行命令。**

## 7. 资源命名 ✅

**本章是资源命名的唯一权威来源**，[art-spec.md](./art-spec.md) 第 9 节只做引用，不另维护一份。

### 7.1 目录组织：按类型分目录

```
assets/
├── char/          reimu_idle_00.png  reimu_walk_00.png  reimu_dead_00.png  reimu_spell_00.png
├── bullet/        bullet_reimu_00.png  bullet_marisa_00.png
├── item/          item_heal.png  item_shield_gen.png  item_armor_harden.png  …
├── map/           shrine_tileset.png  shrine_objects.png
└── sfx/           shoot_reimu.ogg  hit_flesh.ogg  shield_break.ogg  …
```

### 7.2 文件命名：`主体_状态_序号`

| 位置 | 规则 |
|---|---|
| 字符集 | **全小写 ASCII**，下划线 `_` 分隔，无空格、无中文、无大写 |
| 结构 | `主体_状态_序号.扩展名`；无状态或状态唯一的资源省略状态段 |
| 序号 | 两位定长 `00` 起（`00`、`01`…），保证文件管理器按名排序时顺序正确 |
| 扩展名 | 全小写：`.png`、`.ogg` |
| 不使用拼音 | `reimu` 而非 `lingmeng`；`marisa` 而非 `moli`（与 §1 "标识符英文"同理，拼音既不好读也搜不到） |

**为什么不带类型前缀**：目录已经表达了类型（`char/reimu_idle_00.png`）。再写 `char_reimu_idle_00.png` 是把同一信息编码两遍，改目录结构时还要批量改名。**类型由目录承担，文件名只管"是谁、什么状态、第几帧"。**

**为什么不带尺寸前缀**：尺寸写在 art-spec 的规格表里，改了尺寸只需重导一次图，不必改所有引用。名字里带 `48x48` 的结果一定是"图改成 64×64 了但名字还留着 48"，比不带更误导。

### 7.3 图集（atlas）

| 项目 | 结论 |
|---|---|
| MVP 是否打包图集 | ❌ **不打包**，单图直载 |
| 例外 | 地图 **tileset 必须是一张索引图**（Phaser tilemap 的硬性要求，按格切分） |
| 加载策略 | **按场景分包**：选人界面只加载 char，对局加载 char + bullet + item + map + sfx |
| 工具 | 不引入 TexturePacker / free-tex-packer |

**为什么 MVP 不打包**：素材总量约 25 个文件，HTTP/2 下 25 个并发请求的开销可以忽略；而图集带来的代价是"每改一张图要重新打包、图集里的帧名要额外约定、出问题时先怀疑是不是图集没更新"。**在数量还少的时候，打包是纯粹的成本。**

**后期怎么升级**：Phaser 加载 atlas 与加载单图的差别只在 `load.atlas()` 与 `load.image()` 两行，渲染侧引用的是帧名而非路径。所以真到需要打包时（比如素材超过 100 张），换加载方式即可，不用动渲染代码。

### 7.4 源文件与原图

| 文件 | 是否入库 | 说明 |
|---|---|---|
| 导出成品（`.png` / `.ogg` / tileset） | ✅ | 运行需要 |
| 美术源文件（`.aseprite` / `.psd` / `.kra`） | ❌ | 放网盘，见 3.3 |
| **AI 生成的原始大图** | ❌ | 体积大（单张数 MB）、可重生成，不入库 |
| **AI 生成用的提示词** | ✅ | 纯文本、极小，是"这张图怎么来的"的唯一记录，必须入库（见 art-spec 4.5 的授权登记要求） |

提示词放在 `assets/char/_prompts.md` 这类与素材同目录的文本文件里，一条记录写清：文件名、工具与版本、日期、完整提示词、生成后的处理步骤。**这张表同时承担 art-spec 4.5 要求的"AI 素材来源登记"。**

## 9. 协作约定 ✅

| 条目 | 内容 | 状态 |
|---|---|---|
| **`shared/` 改动预告** | **动 `shared/` 里的核心逻辑（伤害结算、弹道、护盾、复活）前，先在群里说一句"我要改 XXX"** | ✅ |
| 任务分配 | **按模块切分**（客户端 / 服务端 / 美术），避免多人同时改同一文件。跨模块的改动（尤其动 `shared/`）先预告再动手 | ✅ |

| 争议处理 | 先回到需求文档判断"这是不是需求问题"：是则讨论需求，不是则按技术最优解定，**不在实现层反复拉锯** | ✅ |
| 进度同步 | 每次合并到 `main` 后，在群里用一两句话说明改了什么、当前还有什么没做完 | ✅ |

💡 关于 `shared/` 预告这一条：它零成本，但能消掉大部分冲突。冲突的真正来源不是"规范不够细"，而是**两个人都不知道对方正在改同一处**。一句预告就能解决。

**这五条的共同点**：都不需要工具支持、不需要流程审批，只要求"说一句"。本项目人少、无评审环节（3.2），沟通成本就是唯一的协调机制，所以这几条不是形式，是替代评审的那部分功能。

## 10. 人员进出 ✅

本项目的参与者是流动的：有人随时想加入，有人中途有事退出。这一章把这两种情况写清楚，避免"人走了不知道该找谁"或"新人来了没人带"。

### 10.1 新成员上手清单

按顺序做，半天内应该能跑起来：

| # | 步骤 | 说明 |
|---|---|---|
| 1 | 读文档 | 只读两份就够上手：`requirements.md` 第 2–5 章（玩法与模式）、`tech-design.md` 第 2、8 章（架构决策与目录结构） |
| 2 | 装环境 | Node 22 LTS；编辑器推荐 VS Code，装 ESLint 插件 |
| 3 | clone 后切到 `dev` | **不要留在 `main` 上开发**（见 3.1 规则 4） |
| 4 | 装依赖并启动 | `npm install` → `npm run dev`（具体脚本名以仓库实际为准） |
| 5 | 先跑一次离线练习场 | 不连服务器也能跑，这是验证环境装对最快的方式 |
| 6 | 认领任务 | 从 `dev` 拉 `feat/xxx`，改动前在群里说一声 |
| 7 | 提交前自检 | 能启动、`shared/` 没引入框架、提交信息带前缀且写了为什么 |

**给新人的三条禁令**（都是本项目的特殊约定，与一般项目不同）：

1. **不要用引擎自带的物理/碰撞**，战斗逻辑必须写在 `shared/`（需求 10.2.3）
2. **不要在 `shared/` 里 import Phaser、ws、node 模块或 DOM API**（tech-design 8.2）
3. **不要自行调整数值**，数值由项目负责人决定（见 9 章）

### 10.2 退出交接

有人中途退出时，交接**三样东西**，缺一样都会留坑：

| 交接项 | 具体做法 | 不交接的后果 |
|---|---|---|
| 未完成的分支 | 在群里说明：做到哪一步、还差什么、有没有踩过的坑；分支**保留不删**，命名加 `wip/` 前缀 | 后来者重做一遍，或者踩同一个坑 |
| 持有的权限 | 仓库、服务器、网盘、群管理等权限移交给固定的人 | 权限锁在离开的人手上，需要改配置时动不了 |
| 未写进文档的知识 | 口头约定、试过的失败方案，当场补进文档 | 文档与实际不符，比没文档更糟 |

**关键岗位必须有备份**：仓库管理、服务器部署、数值决定这三件事，任何一件只有一个人会做，都是项目风险。人员流动是常态，**不要让任何关键操作只存在于一个人的手上**。
