## 1. 项目概述

### 1.1 一句话定位

一款基于东方 Project 题材的 **Web 端平面弹幕竞技游戏**：玩家操控东方角色在俯视视角的大地图上移动、瞄准、射击，通过走位与预判击败对手，并用角色的专属符卡打出高光时刻。

### 1.2 项目性质与边界 ✅

| 项目 | 内容 |
|---|---|
| 性质 | 东方 Project 二次同人创作 |
| 分发范围 | **仅同好群内部分发，不公开发行** |
| 商业化 | **不商业化**：不收费、不内购、不投放广告、不接受赞助 |
| 使用场景 | 群友之间异地联机娱乐 |
| 运营强度 | 无正式运营，无客服、无用户增长目标 |

这条边界决定了大量功能被排除：**不需要账号体系、不需要支付、不需要反作弊系统、不需要公开匹配大厅、不需要运营埋点与用户行为分析**。任何后续需求都应先通过这条边界检验。

> 注：§10.7 的"对局日志"不属于此处排除的埋点——它是为调平衡服务的技术日志，记录的是对局结果而非用户行为，两者不冲突。

### 1.3 目标玩家

- 东方 Project 爱好者，对角色与符卡有认知
- 能接受 Web 端键鼠操作的轻度竞技玩家
- 预期同时在线规模：单个房间 2–8 人（PvP 混战最低 3 人），同时可能存在 1–3 个房间

### 1.4 参考作品

| 作品 | 借鉴的部分 |
|---|---|
| 《弓箭手大作战》(Archero 类 / .io 类竞技射击) | **核心参照**：平面俯视、稀疏弹道、走位对枪、单局制竞技节奏 |
| 东方 Project 系列 | 题材与角色、符卡概念、弹幕的美学表达、Boss 战 |

### 1.5 差异化定位

东方原作的乐趣是"在密集弹幕中极限走位"（躲避向），本项目选择的是"**稀疏弹道下的人际对枪**"（预判向）。因此：

- **不追求满屏弹幕**，而是让每一发子弹都有重量，命中靠预判和走位博弈
- 东方元素通过**角色、符卡、美术、Boss 战**承载，而非通过弹幕密度承载
- 符卡是唯一的"爆发时刻"，用来制造与稀疏射击形成反差的爽感

> 这一取舍的代价：辨识度不如密弹幕方案。若后续觉得"不够东方"，可考虑增加"符卡释放时的密集弹幕"作为弥补手段（💡 待验证）。

## 2. 核心玩法

### 2.1 核心循环

```
进入房间 → 选择角色 → 准备 → 倒计时开局
   ↓
移动走位 → 瞄准射击 → 命中扣血 → 击倒对手/怪物 → 得分或推进
   ↓                    ↑
拾取地图道具（短暂增益）  └── 释放符卡（冷却好了就用）
   ↓
达成胜利条件 → 结算面板 → 下一局 / 返回大厅
```

### 2.2 操作方式 ✅

| 操作 | 输入 |
|---|---|
| 移动 | W / A / S / D（八方向） |
| 瞄准 | **光标绝对定位**：光标在屏幕上的位置就是瞄准点，角色朝向光标 |
| 射击 | 鼠标左键（按住连射 或 点击单发，⬜ 待定） |
| 释放符卡 | 键盘单键（⬜ 具体按键待定，建议 Space 或 Q） |
| 全屏切换 | 提供按键/按钮（⬜ 具体按键待定） |
| 菜单 | ESC |

**键位可自定义** ✅：默认 WASD 布局，玩家可在设置中改键。改键结果本地保存。

**明确不做**：冲刺/闪避键、近战攻击、换弹/弹药系统、蹲下、跳跃。
操作层只有"移动 + 射击 + 符卡"三层，这是刻意的克制，目的是降低上手门槛、保证 Web 端操作精度。

#### 关于鼠标锁定与灵敏度 ✅

本项目的瞄准采用**光标绝对定位**，因此：

| 项目 | 结论 | 原因 |
|---|---|---|
| 鼠标锁定（Pointer Lock） | ❌ **不做** | 锁定会把光标固定在屏幕中心，`光标绝对定位`就失效了，角色无法瞄准。两者互斥 |
| 灵敏度设置 | ❌ **不做** | 光标位置即屏幕绝对坐标，鼠标位移与光标位移的换算由系统 DPI 决定，游戏内不存在"转多少角度"这个环节，没有可调的量 |
| 光标移出窗口 | 限制在窗口内 | 用 CSS cursor 限制与全屏运行来规避，避免瞄准丢失 |

💡 若后续实测发现"光标贴屏幕边缘时大范围转身困难"，可再讨论是否增加"锁定 + 虚拟准星"的备选模式。当前不做。

### 2.3 战斗判定与节奏

#### 2.3.1 弹道 ✅

- 所有攻击都是**飞行投射物**，有可见轨迹和飞行时间，不是瞬间命中（hitscan）
- 弹道可被墙体阻挡，需要预判敌人走位
- 命中判定为投射物与角色的碰撞

#### 2.3.2 击杀时长目标：TTK 与护盾耐久 ✅

护盾等价于"一段会自动恢复的额外 HP"（见 2.3.3），两者使用同一套扣除机制、同一个计量单位，因此可以直接相加。

| 指标 | 定义 | 目标值 | 单位 |
|---|---|---|---|
| **TTK** | 白值对射下，把满 **HP** 打到 0 所需时间 | 5–10 秒 | 秒 |
| **护盾耐久** | 白值对射下，把满 **护盾** 打空所需时间 | 2–4 秒 | 秒 |
| **实际击杀时长** | 上述两者相加 | **8–13 秒** | 秒 |

**护盾耐久一律以"秒"计量，不再用"打几发"表达。** 原因是不同角色射速差异很大（散射型单发弱、射速快），"3–5 发"在不同角色身上对应的时长可能差一倍，无法作为跨角色的共同目标。需要换算成发数时，由具体角色的单发伤害与射速反推即可，但那只是推导结果，不是设计目标。

**为什么要拆开**：

- 若只写"击杀 5–10 秒"而不区分护盾，实际击杀会变成 8–13 秒，与玩家感受到的对不上
- 若把护盾并进 TTK 统一计算，"HP 与护盾的比例"就变成一个隐藏的调节参数，改一个动全身
- 拆开后两个数各自简单、各自可独立调；只要守住"相加 8–13 秒"这条线，整体手感不会跑偏

**其他锁定项**：

- 上述数值均指白值、无增益、无掩体、双方站桩互射的条件
- 项目负责人明确：**通过限制"增加 HP 的途径"来调节激烈度**，不希望出现血量膨胀导致对射变长
- 具体数值在角色数值设计阶段填入，本文档只锁定区间与相互关系

#### 2.3.3 伤害与护盾计算 ✅

**结论：防御即护盾值，等价于"一段会自动恢复的额外 HP"。**

伤害结算顺序：

```
受击 → 先扣护盾（1 点伤害扣 1 点护盾）→ 护盾归零后，溢出部分扣 HP → HP 归零则阵亡
```

- 护盾的扣除机制与 HP **完全相同**：不做倍率、不做减伤公式、不做独立层计算
- 它与 HP 的唯一区别是**会自动恢复**（见 2.3.4）
- 护盾不参与伤害公式，只做**抵消**
- 唯一例外是「防御强化」道具生效期间护盾吸收量翻倍（见附录 A.3），这是临时的道具效果，不是常驻规则
- HP 与护盾在 HUD 上**分别显示**（见 8.3）

#### 2.3.4 护盾恢复 ✅

| 规则 | 内容 |
|---|---|
| 触发条件 | **脱战**后开始回复 |
| 脱战判定 | 连续 **5 秒**未受到伤害即视为脱战（暂定值，可调） |
| 回复方式 | 每秒回复固定数值（暂定值，需结合各角色的护盾上限与 HP 量级确定） |
| 可被刷新 | 回复过程中再次受到伤害，脱战计时重置，回复中断 |
| 上限 | 回复不超过该角色的护盾上限 |

**回复速率必须显著低于输出速率** —— 这是机制层面的硬约束，不是调参偏好。

理由是脱战阈值（5 秒）短于一次完整的实际击杀时长（8–13 秒，见 2.3.2）。如果回复太快，进攻方在绕掩体、走位、躲避的间隙就会被对方把护盾回满，结果只有两种：要么"永远打不死人"，要么"打一下就跑、等盾回"变成唯一最优解，两种都会毁掉对射节奏。

由此得到一条设计约束：

> **连续 5 秒内回复的护盾量，不得抵消一次交火（8–13 秒）所造成的护盾消耗。**

参考换算：若一次交火能打掉一半护盾，则脱战 5 秒的回复量应明显低于该值（例如不超过护盾上限的 15%–20%）。具体数值在角色数值确定后调参。

⬜ 待定：护盾回复速率的具体值、以及从脱战到回满所需的总时长（开发期调参）。

### 2.4 视野与信息呈现 ✅

这是本项目与普通 .io 射击差异较大的一环，规则需要精确。

| 场景 | 规则 |
|---|---|
| 镜头 | 跟随玩家，地图远大于一屏 |
| 视线遮挡 | **墙体与掩体遮挡视线**，被遮挡区域内的敌人不渲染 |
| 小地图性质 | ✅ **开阔区雷达 + 掩体后记忆**，两种机制叠加 |
| 雷达部分 | 小地图显示半径 **大于** 屏幕可视半径。半径内、且与玩家之间**无墙体遮挡**（视线可达）的敌人，**实时**显示在小地图上 |
| 记忆部分 | 半径内但**被墙体遮挡**（视线不可达）的敌人不实时显示；若此前曾显示过，则保留其**最后已知位置**标记，持续一段时间后消失（时长可配置） |
| 视野内 | 屏幕可视范围内的敌人正常渲染 |
| 自己 | 始终在小地图中心显示 |

**设计意图**：小地图是一台"有视线限制的雷达"，不是全知雷达。

- **雷达半径内的开阔地带，敌人全程暴露** —— 正面对抗时信息透明，胜负看操作，不看谁先发现谁
- **掩体才是唯一的信息屏障** —— 因此偷袭必须依赖掩体，不能依赖距离。这也解释了为什么地图需要有足够多的墙体和拐角（见 5.2）
- **"最后已知位置"** 给被偷袭方留下反应线索，避免纯信息碾压

⚠️ 这条规则曾存在两种理解（纯雷达 / 纯记忆）。现已明确为"开阔区雷达 + 掩体后记忆"，实现时不要只做其中一半。

✅ **团队战：队友位置始终显示**，且队友看到的敌人会共享标记到自己小地图（规则详见 4.3）。

⬜ 待定：混战模式下是否在小地图标出道具刷新点；PvE 模式下是否标出 Boss 位置。

### 2.5 反馈与敌我辨识 ✅

#### 2.5.1 命中与受击反馈

每次命中和受击都必须有明确的视听反馈（受击闪白、伤害数字、命中音效），否则稀疏弹道下玩家会难以判断是否打中。这是手感的硬性要求。

#### 2.5.2 敌我辨识 ✅

在保留各角色原有美术风格的前提下，**给敌方角色与敌方弹幕的外轮廓加一圈红色荧光**，用于区分敌我。

要求：
- 红色描边必须**不遮挡角色本体**，只包在外轮廓
- 敌方弹幕描边要考虑**粗细与亮度**，不能因为描边反而看不清弹道
- 多人混战时，除自己以外所有人都是"敌方"，统一红色描边
- 团队战中，队友**不加**红色描边（便于快速区分敌我）
- ⭐ **隐身会移除描边**：隐身者身上的红色描边与其弹幕描边同时消失，小地图标记一并移除。详细规则见附录 A.1.3
- ⬜ 待定：色弱玩家是否提供描边颜色替换（如红/蓝可选）

⬜ 待定：是否需要"队友描边"（如淡蓝）以进一步区分三人以上混战的场面。

### 2.6 移动与碰撞规则 ✅

| 规则 | 结论 |
|---|---|
| 角色之间 | ✅ **不碰撞**，可以互相穿过 |
| 角色与墙体 | ✅ 碰撞，不可穿过 |
| 角色与道具 | ✅ 不碰撞，走上去即拾取 |
| 子弹与角色 | ✅ 碰撞即命中 |

**为什么角色之间不做碰撞**：角色互撞会带来"卡位""堵门""被队友挡住"这类问题，在 8 人混战和团队战里容易变成互相卡死。不做碰撞意味着走位完全自由，胜负只取决于射击精度与走位预判，也避免了"被队友堵在门口"的情绪成本。

⬜ 待定：角色是否有体积（碰撞半径）——影响子弹命中判定，属于数值范畴，标为待定。

## 3. 角色与战斗系统

### 3.1 属性体系 ✅

每个角色包含以下要素：

| 要素 | 说明 | 状态 |
|---|---|---|
| HP | 生命值，归零则阵亡 | ✅ |
| 防御 | **护盾值**，先于 HP 被扣除，脱战可回复，规则见 2.3.3、2.3.4 | ✅ |
| 移速 | 移动速度，单位 px/s 或格/s | ✅ |
| 被动 | 常驻效果，无需操作触发 | ✅ |
| 弹幕（主武器） | 角色的普通攻击方式 | ✅ |
| 符卡（特殊技） | 冷却制的强力技能 | ✅ |

⬜ 是否需要攻击力作为独立属性，还是把伤害直接写进"弹幕"配置里（建议后者，减少属性维度）。

### 3.2 弹幕（主武器）

每个角色一套独立的普通攻击，差异化体现在：

- 单次发射的弹丸数量（1 发 / 3 发扇形 / 5 发散射）
- 射速（攻击间隔）
- 单发伤害
- 弹速与射程
- 弹丸体积
- 特殊行为：穿透、轻微追踪、命中溅射、回弹（💡 建议 MVP 只做前 5 项，特殊行为后续加）

### 3.3 符卡（特殊技）✅

| 项目 | 规则 |
|---|---|
| 释放方式 | **纯冷却制**，冷却结束即可再次释放 |
| 资源消耗 | 无。不消耗能量、不限次数、不需要充能 |
| 数量 | 每个角色 1 张（⬜ 是否需要 2 张待定） |
| 强度定位 | 强力但可被走位规避，不能是"必中必杀" |
| 冷却时长 | 按角色定位设定，⬜ 数值待定 |

⬜ 待定：符卡释放时是否有前摇/施法动作、是否可被打断、是否有全局播报（"某某释放了符卡"）。

### 3.4 被动

常驻效果，例如"受到伤害时短暂加速""击杀后回复少量 HP""符卡冷却加快"等。每个角色 1 个（⬜ 待定）。

### 3.5 局内成长 ✅

**结论：PvP 模式无局内成长，PvE 模式有局内成长。**

| 模式 | 局内成长 | 说明 |
|---|---|---|
| PvP 混战 | ❌ 无 | 全程白值，局内强度只来自地图道具 |
| PvP 团队战 | ❌ 无 | 同上；多局之间也不继承任何成长 |
| PvE 波次 | ✅ 有 | 否则无法应对逐波递增的敌方强度 |
| 单人练习场 | ❌ 无 | 但提供调试用开关（无敌、无限符卡等） |

**设计意图**：PvP 的公平性优先。双方同等条件下，胜负只取决于操作、走位与道具争夺，不取决于谁先打了更多小怪。这条与 2.3.2「通过限制增加 HP 的途径来调节激烈度」是同一个原则。

⬜ 待定（PvE 成长的具体形式）：升级三选一 / 固定等级数值成长 / 击杀积攒资源在波次间消费。**该内容随第二阶段 PvE 一起设计并交付，不属于 MVP 范围**（见 12.2）。

### 3.6 首版角色 ✅

MVP 阶段只做两个角色，用于验证手感、联机与平衡框架：

| 角色 | 定位方向（💡 待设计） |
|---|---|
| 博丽灵梦 | 建议偏向均衡/直线型，弹道清晰、符卡为范围压制 |
| 雾雨魔理沙 | 建议偏向高输出/散射型，弹道密集但单发弱、符卡为直线爆发 |

具体技能组（弹幕形态、符卡效果、被动、数值）⬜ 待角色设计阶段产出，本文档不预设。

## 4. 游戏模式

### 4.1 模式总览 ✅

| 模式 | 性质 | 核心目标 | 交付阶段 |
|---|---|---|---|
| PvP 混战 | 玩家互相对抗 | 限时内获得最高分数 | ✅ MVP |
| PvP 团队战 | 阵营对抗 | 赢下足够局数 | 1.1 |
| PvE 波次 | **纯合作**，玩家之间无伤害 | 抵御波次，击败 Boss | 第二阶段 |
| 单人练习场 | 离线，无对抗 | 练手与调试 | ✅ MVP |

### 4.2 PvP 混战（Free-for-All）✅

| 项目 | 规则 |
|---|---|
| 人数 | **3–8 人**，可灵活设置。少于 3 人无法开始 |
| 中途加入 | ✅ **允许**。新玩家可在对局进行中加入，加入时计 0 分 |
| 时长 | 限时，⬜ 默认时长待定（建议 3–5 分钟） |
| 阵亡与复活 | **可以复活**。阵亡后等待 **5 秒**（暂定），在**离最近敌人最远的出生点**重生 |
| 复活保护 | 重生后有短暂无敌保护，⬜ 时长暂定（建议 1–2 秒） |
| 胜负 | 时间结束时按**分数**结算排名 |
| 计分规则 | ✅ **击杀 +1，死亡不扣分** |

**计分说明**：死亡不扣分是为了让新手不至于越玩越负，混战模式下不设惩罚。这意味着"送人头"不会拉低自己的排名，但会拉开与对手的差距，博弈动力仍然存在。

**复活点选择**：在所有出生点中，计算每个点到"最近的存活敌人"的距离，取距离最大的那个点重生。若无存活敌人，则随机选取。这样避免复活即被抓。

**中途加入与人数下限的配合**：混战允许中途加入，因此人数跌破 3 人时**不会立即结算**，而是给 **20 秒宽限期**等待补人（见 7.5）。这样"3 人局掉一人"不会立刻把对局终止掉，而真正无人可补时才收场。

⬜ 待定：重生时的视觉提示（是否需要短暂的高亮/光柱让对手知道有人重生了）。

### 4.3 PvP 团队战 ✅

| 项目 | 规则 |
|---|---|
| 人数 | 房主可选择 **1v1 / 2v2 / 3v3 / 4v4**。若人数为除不尽的奇数，房主可**强行开始**，形成不对称对局（如 5 人局即 3v2） |
| 中途加入 | ❌ **不允许**。团队战必须在开局前确定阵容，中途加入会破坏局数平衡 |
| 友伤 | ✅ **无友伤**。子弹穿过队友，不造成伤害、不被队友阻挡 |
| 视野 | ✅ **团队共享视野**。队友位置始终显示在小地图上；队友看到的敌人会共享标记到自己的小地图 |
| 沟通 | ✅ **不做内置语音**，依靠第三方语音工具；游戏内提供**快捷信号**（见 4.3.1） |
| 复活 | **可配置每个玩家的复活次数** |
| 复活耗尽 | 该玩家本局出局，不再参战（可观战） |
| 单局胜负判定 | ✅ **复活耗尽优先，超时比击杀**，见下方说明 |
| 胜负 | **几局几胜**（如 BO3、BO5，可配置） |
| 单局时长 | 限时，⬜ 待定 |

**关于视野的说明**：本条曾一度确定为「各自视野」，后由项目负责人更正为**共享视野**。理由是团队战若各自独立视野，队伍会退化成四名单打独斗的玩家，"团队"这一层玩法就失去了意义。共享视野让"报点"和"集火"变得可能。

共享的是**敌人标记位置**，不共享的仍是**画面本身的可见区域**——即队友能提供目标坐标，但自己看不到队友屏幕里的画面。

**单局胜负判定**：

| 情形 | 判定 |
|---|---|
| 一方全员复活耗尽 | 该方**判负**，本局立即结束，不等计时器 |
| 限时结束，双方均仍有存活玩家 | 按本局**击杀总数**判胜 |
| 限时结束，双方击杀总数相同 | ✅ **判平**，该局不计入任何一方胜场 |

**平局的后续处理**：判平的一局直接跳过，进入下一局。若打满配置的局数仍无人达到所需胜场，则以**胜场多者**获胜；若胜场也相同，整场判平。⬜ 待定：是否需要"平局加时"作为可选开关。

⬜ 待定：队友标记是否在屏幕边缘以箭头形式指出屏外队友的方向。

#### 4.3.1 快捷信号 ✅

不做内置语音，但必须有非语音的配合手段，否则"共享视野"提供的队友信息无法互相传递，团队战会退化成四个人各打各的。

| 项目 | 内容 |
|---|---|
| 形式 | 快捷键呼出信号轮盘，或单键直接发送预设信号（⬜ 二者取舍待定） |
| 预设条目（⬜ 具体条目待定） | 敌人在这里 / 需要支援 / 小心埋伏 / 集合 / 撤退 |
| 展示 | 图标 + 小地图标记 + 短促音效，全队可见，持续数秒后消失 |
| 限制 | 有冷却时间，避免刷屏干扰 |
| 广播范围 | 仅本队可见，敌方不可见 |

⬜ 待定：信号是"指向式"（能标到具体地图坐标）还是"预设式"（只能发固定语句）。指向式配合更好，但需要额外的交互设计。

### 4.4 PvE 波次模式 ✅（第二阶段交付）

| 项目 | 规则 |
|---|---|
| 性质 | **纯合作**，玩家之间不会互相造成伤害 |
| 结构 | 分波刷怪，波次强度递增 |
| Boss | **周期性出现 Boss**（每 N 波），Boss 拥有多阶段攻击模式与弱点 |
| 失败条件 | ⬜ 待定。候选：全员阵亡即失败 / 有共享生命池 / 无视死亡只算波数 |
| 胜负 | ⬜ 待定。候选：无尽模式（活得越久越好）/ 固定波数通关 |

⬜ 待定：怪物类型设计、Boss 数量、波次间隔时间、是否需要在两波之间给玩家补给。

✅ **已确认：PvE 不纳入 MVP，放到第二阶段交付。** 理由是 Boss 需要美术、AI 与关卡设计三块额外投入，会拖慢核心玩法（PvP 手感与联机）的验证，而后者才决定这个项目值不值得继续做。具体见 12.1。

### 4.5 单人离线练习场 ✅

| 项目 | 规则 |
|---|---|
| 运行方式 | **完全本地，不连接服务器**，可断网运行 |
| 用途 | 开发者调试手感 / 平衡；新人熟悉操作。**本项目不做新手引导，练习场即上手入口** |
| 功能 | 自由调参（无敌、无限符卡、显示碰撞盒、显示弹道轨迹）、生成静止假人或会移动的假人、快速切换角色 |
| 地图 | 复用正式地图，可强制开启全图视野 |

✅ **已纳入 MVP。** 它让"调手感"这件事不需要每次都开服务器、叫上另一个人，在验证阶段的价值尤其明显（见 12.1）。

### 4.6 模式参数表

以下参数应全部做成**房主可配置**，而非硬编码：

| 参数 | 混战 | 团队战 | PvE |
|---|---|---|---|
| 人数 | 3–8 人 | 1v1 / 2v2 / 3v3 / 4v4，奇数可强开不对称局 | 2–8 人 |
| 单局时长 | 可配 | 可配 | — |
| 复活次数 | 无限 | 可配 | ⬜ |
| 局数（几局几胜） | — | 可配（BO1/BO3/BO5） | — |
| 是否友伤 | — | ❌ 无 | ❌ 无 |
| 中途加入 | ✅ 允许 | ❌ 不允许 | ⬜ |
| 地图选择 | 可配 | 可配 | 可配 |

⚠️ **交付阶段**：只有**混战**在 MVP 范围内。**团队战为 1.1 交付、PvE 为第二阶段交付**（见 12.1、12.2）。本表保留团队战与 PvE 的参数定义，是为了提前锁定配置项的形状，不表示它们要在 MVP 一起实现。

### 4.7 结算与统计 ✅

每局结束后展示结算面板，**统计维度固定为以下四项**：

| 维度 | 说明 |
|---|---|
| 击杀数 | 本局击杀的敌人数 |
| 死亡数 | 本局阵亡次数 |
| 对敌方造成的总伤害 | 累计有效伤害（护盾吸收的部分是否计入 ⬜ 待定） |
| 捡到的道具数 | 本局拾取的道具数量 |

- 混战模式按分数排列名次，团队战按阵营胜负呈现，PvE 按波次与总伤害呈现
- 这四项数据必须由服务端统计并下发，不能由客户端自行上报

⬜ 待定：
- 伤害统计是否包含被护盾吸收的部分（建议包含，否则"打了半天全是护盾"的玩家统计会很难看）
- 是否需要"最速击杀""最高连杀"这类趣味项（❤️ 锦上添花，非必需）

✅ **不保存历史战绩**：结算数据仅在当局有效，关闭页面即清空，不做任何持久化。

### 4.8 观战 ✅（1.1 交付）

**适用范围**：

| 模式 | 观战 | 说明 |
|---|---|---|
| PvP 团队战 | ✅ 需要 | 复活次数耗尽的玩家自动进入观战 |
| PvP 混战 | ❌ 不需要 | 混战是复活制，阵亡只需等待 5 秒重生，不存在"出局后干等"的场景 |
| PvE | ⬜ 待定 | 第二阶段再定 |

⚠️ **观战随团队战一起移出 MVP，放到 1.1 交付。** MVP 只做混战，而混战没有观战需求，因此 MVP 内不包含观战功能。

#### 4.8.1 观战范围 ✅

| 能力 | 1.1 | 说明 |
|---|---|---|
| 跟随离自己最近的存活队友 | ✅ 做 | 默认视角 |
| 切换跟随其他队友 | ✅ 做 | |
| 自由拖动镜头 | ❌ 不做，延后至后续阶段 | 需要一个独立的可见性判定，成本高于当前阶段的收益 |
| 显示护盾/符卡等详细信息 | ⬜ 待定 | |

只做"跟随队友 + 切换队友"，因为它复用现有镜头系统，成本低，但足以解决"阵亡后盯着静止画面等下一局"的体验断裂。

#### 4.8.2 已记录但延后的约束：自由视角的视野限制 ✅

这条规则在做自由视角时必须遵守，现在先记录，避免将来实现时漏掉：

观战者能看到的敌人，**只能来自团队视野**（见 4.3）。自由拖动镜头只改变镜头位置，**不会看到更多敌人**。

- 镜头拖到敌方附近，若该位置不在任何队友视野内、且没有小地图标记，这里**就是空的**
- 敌方标记仍遵守"进入掩体后保留最后已知位置，超时消失"的规则（见 2.4）
- 观战所见 ≈ 团队实时所能获知的信息，不多不少

**为什么限制**：观战者若能看到上帝视角，就可以在第三方语音里报点，等于给团队开了一个外挂。这条让观战不产生任何额外的信息优势，保护对局公平。

## 5. 地图与场景

### 5.1 尺寸与视野 ✅

- 地图**远大于一屏**，镜头跟随玩家
- 具体尺寸 ⬜ 待定
- ✅ 设计目标：8 人混战时，两名玩家平均 **10–20 秒**内能遭遇一次。太大会变成"跑图游戏"，太小则失去掩体与绕后的意义
- 该值由 30–60 秒收紧而来：单局只有 3–5 分钟，按 30–60 秒计算一局仅能遭遇 3–6 次、六成以上时间在跑图，与"稀疏弹道、快节奏对枪"的定位不符

### 5.2 地形元素

| 元素 | 阻挡移动 | 阻挡子弹 | 遮挡视线 |
|---|---|---|---|
| 墙体 | ✅ | ✅ | ✅ |
| 低矮掩体 | ⬜ 待定 | ✅ | ⬜ 待定 |
| 开阔地 | ❌ | ❌ | ❌ |

⬜ 待定：是否区分"高墙"和"低矮掩体"两种阻挡级别。区分会增加美术与碰撞的工作量，但能带来"能射击但看不见"的战术层次。

### 5.3 地图边界与出界规则 ✅

**是否封闭，取决于具体地图的设计需要**，不是全局统一规则。因此地图配置中需要一个"边界类型"字段：

| 边界类型 | 行为 | 适用 |
|---|---|---|
| 封闭墙 | 地图四周是墙体，无法离开场地 | 室内、遗迹、封闭竞技场 |
| 开放边界 | 可以走出场地边缘，但**出界持续一段时间后被传送回场** | 室外、山地、开阔地带 |

**开放边界的规则**：
- 走出边界后开始计时（时长暂定，建议 2–3 秒），期间有视觉提示（如屏幕边缘变红、倒计时）
- 超时后传送回最近的合法出生点，并清空该次计时
- 传送回来时 ⬜ 是否需要惩罚（扣血/扣护盾）待定
- 传送回来时若正处于交火中，⬜ 是否给予短暂保护待定

⬜ 待定：边界外是否允许射击（打得到外面的人，还是完全无法交互）。

### 5.4 首版地图 ✅

MVP 阶段 **1 张地图**，要求包含：掩体走廊、开阔争夺区、至少 2 个道具固定刷新点、多方向出生点。

### 5.5 地图扩展

新地图随版本更新加入，设计上应保证不同地图的"掩体密度/开阔区比例"有区分度，形成不同的玩法倾向。

## 6. 道具系统

### 6.1 生成规则 ✅

两条并行的生成途径：

| 途径 | 规则 |
|---|---|
| 固定刷新点 | 地图上预设若干固定位置，按固定间隔定时刷新。形成玩家争夺焦点 |
| 随机地点 | 按固定间隔在可行走区域内随机位置刷新。增加局势变化 |

- 两类的刷新间隔均为**可配置参数**
- ⬜ 待定：同屏道具数量上限、刷出时是否有视觉提示（光柱/音效）、道具是否会被覆盖消失

### 6.2 拾取规则 ✅

**结论：自动拾取。** 角色走到道具上即拾取，无需按键。

理由：不增加操作负担，符合 2.2 中"操作只有三层"的克制原则。若改成按键拾取，会与"手上只有移动、射击、符卡三个动作"的设计冲突。

⬜ 待定：是否需要拾取者标记（让其他人知道道具被谁拿了）。

### 6.3 效果原则 ✅

1. **短暂增益**：所有道具效果都有明确持续时间，到期消失（回血类为瞬时效果）
2. **不叠加**：同类增益再次拾取时**刷新持续时间**，而非叠加数值或叠加层数
3. **有迹可循**：增益生效时角色身上有视觉表现，对手能看出"他现在有增益"
4. **不做永久成长**：道具不改变角色的基础属性上限

### 6.4 可扩展性要求 ✅（架构级需求）

项目负责人明确要求：**后续更新能不断加入新类型的增益**。

因此道具系统必须是**数据驱动**的，具体要求：

- 每个道具由一份配置定义：`id、名称、图标、效果类型、效果参数、持续时间、刷新权重、是否稀有`
- 新增道具应当是"加一行配置 + 加一个图标 + 如果有全新效果类型则注册一个效果处理器"，**不需要改动战斗主逻辑**
- 效果类型应抽象为可组合的原子效果（如"修改某属性倍率""增加护盾值""立即回复 HP""隐藏小地图标记"）

这条要求会直接影响技术方案的设计，技术选型时必须满足。

### 6.5 首版道具清单 ✅

**结论：首版做 8 种**（完整效果参数见附录 A）：

治疗包、护盾发生器、防御强化、攻击强化、射速强化、移速强化、隐身、符卡加速。

选型理由：覆盖「续航 / 防御 / 输出 / 机动 / 技能」五个维度各一到两项，且都不改变角色的基础操作方式，便于在验证阶段观察平衡问题。其余候选道具（多重射击、穿透、双刃、缓速场等）顺延到后续版本，见附录 A 的状态列。

⚠️ 说明：其中「防御强化」因防御已改为护盾制，原「减伤」定义失效，现已改为**护盾硬化**（1 点护盾可吸收 2 点伤害），详见附录 A.3。

## 7. 房间与流程

### 7.1 大厅 ✅

| 功能 | 说明 |
|---|---|
| 创建房间 | 设置模式与参数，生成房间号 |
| 加入房间 | 输入房间号 / 点邀请链接直接进入 |
| 房间列表 | ⬜ 待定是否做。内部娱乐场景下，"房间号 + 群内发链接"的体验可能比列表更简单 |

### 7.2 房主权限 ✅

房主可配置：模式（混战/团队战/PvE）、人数与分组（混战 3–8 人 / 团队战 1v1–4v4）、单局时长、复活次数、局数、地图。

⬜ 待定：开局后房主能否中途修改对局参数。

（房主掉线顺延、主动转让规则已确定，见 7.5。）

### 7.3 局内流程 ✅

```
房间 → 选角色 → 标记准备 → 全部准备后倒计时 → 对局 → 结算面板 → 
  ├─ 再来一局（保留房间）
  └─ 返回大厅
```

### 7.4 断线与重连 ✅

**结论：做重连，方案是"保留席位 + 完整快照恢复"。**

| 项目 | 规则 |
|---|---|
| 掉线处理 | 席位保留 **60 秒**（暂定），期间该玩家**仍计入有效玩家数**（见 7.5） |
| 重连方式 | 重新进入房间时，服务端下发**一份完整的世界快照**，客户端用它重建对局画面与状态 |
| 超时 | 保留时长内未重连，席位移除，随即按 7.5 的人数下限规则判定是否需要结算 |
| 对局中退出（主动） | 与掉线区分：主动退出不保留席位，直接移除（见 7.5） |

**为什么成本不高**：混战允许中途加入（见 4.2），服务端本来就必须能为"新进玩家"生成完整快照。重连只是复用同一条链路，不需要单独实现一套。

⚠️ 由此产生一条**实现约束**：重连与中途加入下发的是**快照**而非增量，因此客户端必须支持"从一个快照冷启动整局"这条路径。这条路是共用的，不要写两份。

### 7.5 房主机制与异常流程 ✅

| 场景 | 规则 |
|---|---|
| 房主主动退出 | **自动顺延**：按加入顺序，移交给第二个加入房间的玩家 |
| 房主主动转让 | ✅ 提供**权限转让**功能，房主可自己指定交接对象 |
| 人数跌破下限（混战） | 跌破 3 人后进入 **20 秒宽限期**：期间有新人补进房间则继续对局；宽限期结束仍不足 3 人，则按当前最高分玩家判胜并提前结算，不等计时器走完 |
| 人数跌破下限（团队战） | **某一方有效玩家数为 0** 时，该方判负、本局结束。团队战**不套用"3 人"这条线**，因为 1v1 是合法配置（全场只有 2 名玩家），套用会开局即结算 |
| 混战人数不足 | 少于 3 人无法开始 |
| 团队战人数不整 | 房主可**强行开始**，形成不对称对局（如 5 人局 3v2） |
| 对局中玩家退出（混战） | 直接移除，其分数与击杀记录保留在结算中 |
| 对局中玩家退出（团队战） | ⬜ 待定：保留席位等待重连，还是直接判该玩家出局 |

**关于人数下限的设计意图**：

- **混战**最少 3 人才开得起来，人数跌到 3 人以下时对局已失去意义（变成 1v1 或单人互射）。但混战允许中途加入，所以不能一跌到底就收场——先给 20 秒等人补进来，补不上才按当前分数结算。这条同时覆盖了"全员掉线"的情况，不需要单列一条。
- **团队战**不能套用"3 人"这条线。1v1 合法（全场仅 2 人）、2v2 掉一个人剩 3 人，套用会让合法对局被误结算。团队战改用"某方无人存活即判负"，与 4.3 的单局胜负判定保持一致。

服务端需在宽限期结束时**立即结算**，不等计时器。注意提前结算也应写入对局日志（见 10.7），否则数据里会缺一段。

✅ **"有效玩家"包含处于重连保留席位中的玩家**（见 7.4）。否则一个人网络抖动几秒就会把整局结算掉，太脆弱。保留席位超时被移除后，再计入下限判定。

⬜ 待定：房主是否能在对局中踢人（内部娱乐场景建议提供，用于处理捣乱）。

### 7.6 身份系统与昵称规则 ✅

**只做昵称，不做账号体系。** 进入时输入/记住一个昵称即可，无密码、无注册、无头像上传。

#### 7.6.1 昵称规则

| 项目 | 规则 |
|---|---|
| 唯一性 | ✅ **不要求唯一**，允许重名 |
| 显示方式 | 昵称**本身不做任何修改**，所有玩家统一附加本局序号用于区分 |
| 序号分配 | ✅ **按加入本局的顺序统一编号**，与是否重名无关：`灵梦#1`、`魔理沙#2`、`灵梦#3`……先进入者号小 |
| 生效范围 | **序号仅在当前对局内有效**，退出或换局后重新判定 |
| 目的 | 让对局日志、结算面板、击杀提示能准确区分同名玩家，避免统计串号 |

**设计意图**：不限制昵称是"少管闲事"，自动加序号是"数据不能混"。两者结合既不需要账号体系，又能保证调平衡用的日志数据是干净的。

⬜ 待定：

- 昵称长度限制（建议 2–12 字符）
- 违禁词过滤的词表来源（本地维护一份即可，不需要外部服务）
- 昵称是否允许特殊字符与表情符号

### 8.1 美术风格 ✅

**像素风。**

本章只保留**需求级约束**。分辨率基准、sprite 尺寸、动画帧数、色板策略、资源命名等具体规格，全部移至 [art-spec.md](./art-spec.md)。

需求级约束（不可妥协，详细实现见 art-spec 第 3 章）：

- 子弹必须在任何地图背景上都足够显眼
- 特效不得遮挡判定区域

### 8.2 音效与音乐 ✅/⬜

| 项目 | 决策 |
|---|---|
| 音效 | ✅ **优先采用免费开源、可免费使用的音效库** |
| 方位定位 | ✅ **做完整的 2D 定位音效** |
| 音乐 | ⬜ **待定**，暂不纳入 MVP |

**方位定位的作用**：本项目是镜头跟随 + 大地图 + 掩体遮挡视线，屏幕外和墙后没有任何视觉信息。声音是唯一的预警渠道——右声道更响表示右边有人开火，音量随距离衰减可判断远近，不同角色的枪声音色可判断来者身份。

**定位要求**：
- 所有关键音效（开火、命中、受击、阵亡、符卡、道具拾取）带**左右声道偏移**
- 带**距离衰减**：距玩家越远越轻
- 屏幕外的音效不需要额外的音量增强，保持物理一致性即可
- ⬜ 待定：是否需要"垂直方向"的听感区分（2D 游戏里上下方位难以用双声道表达，可能需要额外的视觉提示）

💡 候选音效来源与技术取舍，见 [art-spec.md](./art-spec.md) 第 8 章。本文只锁定"用免费开源素材"与"做 2D 定位"这两条需求。

### 8.3 HUD 要素

| 元素 | 说明 |
|---|---|
| 自身 HP 条 | 醒目，低血量有视觉警示 |
| 自身护盾条 | ✅ **与 HP 分开显示**（建议置于 HP 条上方、用不同颜色）；脱战回复过程中需有可见的回复表现 |
| 符卡冷却指示 | 冷却进度环/条 |
| 小地图 | 见 2.4 |
| 分数 / 剩余时间 | 混战与团队战必需 |
| 击杀提示 | 谁击杀了谁 |
| 队友标记 | 团队战 **始终显示队友位置**；队友探测到的敌人共享标记到小地图（见 4.3） |
| 增益状态图标 | 当前生效的道具增益与剩余时间 |

## 10. 技术约束（需求侧）

本章只写**需求对技术提出的约束**，不做技术选型。选型、架构、同步模型、部署方案等内容全部在 [tech-design.md](./tech-design.md)，本文只负责提出约束。

> 换算关系：本文的每一条约束都是 tech-design.md 选型的**淘汰条件**，不满足即淘汰方案。

### 10.1 联机环境 ✅

| 项目 | 约束 |
|---|---|
| 部署 | **公网部署**，群友异地联机 |
| 延迟目标 | RTT ≤ 100ms 时，射击与命中手感不应有明显劣化 |
| 房间容量 | 单房间 **2–8 人**依据模式而定：PvE 最低 2 人，**PvP 混战最低 3 人**（见 4.2） |
| 并发规模 | 预期同时 1–3 个房间，总在线不超过 24 人 |

### 10.2 权威性要求 ✅

由于是公网对战，以下判定**必须由服务端裁定**，客户端只做表现与预测：

- 命中判定与伤害计算
- 阵亡与复活
- 道具拾取归属
- 符卡效果生效
- 分数结算

原因：客户端权威在公网环境下既会产生作弊空间，也会导致"我看到打中了但对方没掉血"的体验撕裂。

#### 10.2.1 命中判定的时间基准 ✅

**结论：服务端按"收到开火指令时的当前世界状态"判定命中，不做回溯（延迟补偿）。**

这是一条**知情取舍**，不是实现缺陷：

- 高延迟玩家会感觉"明明瞄中了却没中"。但这个偏差**只发生在横向移动的目标上**——目标迎面来或背身去时，位置误差只改变"什么时候打中"，不改变"是否打中"
- 本项目用飞行投射物而非瞬间命中，玩家本来就必须打提前量。延迟误差和预判误差被合并成同一类，玩家无法区分，练习后会自动补偿
- 实际击杀 8–13 秒需要命中十几次，单发失误的代价只有约 1/15
- 若做回溯，必须连"视线遮挡"一起回溯（否则会打中一个当时看不见的人），成本与 bug 面翻倍，同时会让"进掩体还被打死"变得频繁

**明确不做**：完整的延迟补偿回溯判定。

**但要求保留升级路径**：服务端需保留最近约 200ms 的玩家位置历史与回溯接口。将来若实测确认手感不足，可低成本切换到回溯判定，不需要重构。

#### 10.2.2 客户端预测边界 ✅

| 对象 | 是否预测 | 说明 |
|---|---|---|
| 自己的移动 | ✅ **预测** | 本地立即移动，不等服务端；收到权威状态后校正 |
| 自己的子弹 | ❌ 不预测 | 子弹的生成、飞行、命中全部以服务端为准，客户端只负责渲染 |
| 其他玩家的位置 | ❌ 不预测 | 在两个快照之间插值渲染，平滑但不预判 |
| 伤害与死亡 | ❌ 不预测 | 完全由服务端裁定 |

**为什么只预测移动**：稀疏弹道开火频率低，约 100ms 的出弹延迟表现为"子弹稍晚一点出现"，不会连续抖动；而预测子弹要额外处理"服务端拒绝这批子弹"（玩家其实已阵亡、符卡冷却未完成），复杂度不划算。

#### 10.2.3 世界状态只能有一份 ✅

**要求：战斗逻辑（移动、碰撞、命中、伤害、护盾、道具、复活）必须实现为客户端与服务端共用的同一份代码，且世界状态只存在这一处。渲染层只能读取它，不能持有自己的副本。**

这条推导自 4.5（离线练习场不连服务器也能跑完整对局）：练习场必须能在本地跑完整战斗，那就必然存在一份"不依赖服务端"的完整逻辑；如果联机时再写一份，两份迟早不一致，表现为"显示打中了却没掉血"。

**推论（对技术选型的约束）**：

- 不允许使用引擎或框架自带的物理/碰撞系统来跑对局逻辑（否则会形成第二份世界状态）
- 不允许把对局状态交给前端框架或 UI 层托管
- 该约束优先于"引擎有什么功能就用什么"的一般开发习惯

详见 [tech-design.md](./tech-design.md) 第 8 章的 `shared/` 硬纪律。

### 10.3 成本约束 💡

需要一台公网服务器。对 8 人实时对战、稀疏弹道的场景，带宽需求不高，但不能忽略：

- 该项目**没有收入**，服务器成本需控制在可接受范围（⬜ 具体预算待与项目负责人确认）
- 因此架构不应依赖昂贵的托管服务

### 10.5 数值与内容的更新机制 ✅

**结论：混合方案——客户端内置默认值，联机时以服务端下发为准。**

| 项目 | 内容 |
|---|---|
| 数值归属 | 角色属性、道具参数、地图参数等，以**服务端为唯一真源** |
| 客户端内置 | 内置一份默认配置，供**离线练习场**使用，同时作为服务端下发失败时的兜底 |
| 联机时 | 进入房间 / 对局开始时，服务端下发本次对局使用的完整数值配置 |
| 热更新 | 修改数值后重启服务即可生效，**不需要重新构建部署前端** |
| 两端一致性 | 客户端与服务端必须来自同一份数值源；否则会出现"客户端显示打中了、服务端判定没中"的体验撕裂 |
| 版本不一致 | Web 端的天然优势：提示玩家**刷新页面**即可，不需要做补丁系统 |

**为什么不能只放客户端**：伤害由服务端裁定（见 10.2），服务端必须自己知道数值，不能信任客户端上报的伤害。

**为什么不能只放服务端**：离线练习场和首屏加载需要一份本地兜底，否则断网或接口异常时游戏起不来。

**新增内容的更新方式**：⬜ 待定

- 美术资源（角色贴图、地图 tile）本质上必须随前端发版
- 配置参数（数值、刷新权重、效果参数）可以服务端下发

💡 建议：**资源发版 + 配置下发**。这样"改平衡不用发版，加地图才发版"，对持续调优最省事。

**对技术方案的要求**：服务端需要具备配置加载与版本号机制；客户端需要具备"默认配置 + 远程覆盖"的合并逻辑。

### 10.6 明确不需要的能力 ❌

反作弊系统、账号体系、数据库持久化（除配置外）、CDN 加速（视情况）、日志分析平台。

### 10.7 对局日志与数据统计 ✅

**结论：只做对局日志。不做汇总报表、不做可视化面板、不做排行榜。**

用途只有一个：**调平衡**。回答"魔理沙是不是太强""护盾是不是太厚""哪个道具没人捡"这类问题。

每局结束时，服务端追加一行 JSON 到日志文件，字段至少包含：

| 字段 | 内容 |
|---|---|
| 时间 | 对局开始 / 结束时间 |
| 模式与地图 | 混战 / 团队战、地图 id |
| 对局参数 | 人数、时长、复活次数、局数 |
| 玩家 | 昵称（含当局序号，见 7.6.1）、所选角色 |
| 个人战果 | 击杀数、死亡数、对敌方总伤害、拾取道具数 |
| 对局结果 | 胜者 / 阵营比分 |

**实现要求**：

- 追加写入，不覆盖历史
- 单行 JSON，便于后续用脚本批量统计
- 写入必须异步，日志失败不能阻断对局
- ⬜ 文件切分策略待定（按天 / 按大小）

⬜ 待定：日志存放位置与保留时长。

💡 说明：选择"日志"而不是"报表"，是因为日志里保留了全部原始数据，将来真需要看角色胜率时，写个脚本聚合即可，不用提前把聚合逻辑做进游戏。

## 11. 合规边界

### 11.1 东方 Project 二次创作 ✅

- 遵守 ZUN 公布的二次创作规约（具体条款在技术方案阶段核对最新版本）
- **不商业化**：不收费、不内购、不投放广告、不接受赞助分成
- 不损害原作形象，不将角色用于与东方世界观冲突的演绎

### 11.2 分发 ✅

本节区分两件事：**游戏本体的分发**受严格限制，**开发协作所用的源码托管**不受此限制。二者混淆会导致"仓库公开 = 对外发行"的错误推论，故分开写。

**游戏分发**（约束对象：可运行的游戏本体）

- 仅在同好群内部分发，以群内及受邀成员为限
- 不上架任何公开游戏平台或应用商店，不做公开宣传推广
- 不对外提供公开下载入口，包括公开的试玩链接与公开的构建产物下载页

**源码托管**（约束对象：开发协作）

- 源码仓库可托管在公开代码平台（如 GitHub），用途**限于协作开发与版本管理**
- 源码公开**不构成对任何人的分发授权**：不视为授权他人部署、运营、分发或商用本项目，也不等于对外提供游戏本体
- 仓库内不放可游玩的生产构建产物、公网访问地址；权属与使用限制在仓库 README 中声明
- 引入外部协作者仍按 [dev-conventions.md](./dev-conventions.md) §10「人员进出」处理，不以"仓库已公开"替代人员审核

### 11.3 素材版权 ✅

- 优先使用 CC0 / 开源协议素材，并**在仓库内登记来源与协议**
- 原创美术需与合作开发者事先约定权属与后续使用范围
- 不使用来源不明的网络素材

### 11.4 角色使用

灵梦、魔理沙等原作角色仅作同人演绎，不改变其在原作中的基本定位。⬜ 是否允许原创角色（原创角色会涉及与合作者的创作权属问题，建议 MVP 不做）。

## 12. 范围与里程碑

### 12.1 MVP（首版）范围

目标：**验证"稀疏弹道 + 走位对枪"这套核心玩法是否好玩。**

| 内容 | 是否纳入 MVP |
|---|---|
| 博丽灵梦、雾雨魔理沙 2 个角色 | ✅ |
| 1 张地图 | ✅ |
| PvP 混战模式 | ✅ |
| PvP 团队战模式 | ❌ 移出 MVP，**1.1 交付** |
| 团队战观战（跟随队友 + 切换） | ❌ 移出 MVP，随团队战一起 1.1 交付 |
| 基础道具系统（8 种） | ✅ |
| 符卡系统 | ✅ |
| 护盾（防御）系统 | ✅ |
| 公网联机（含房间创建/加入） | ✅ |
| 单人离线练习场 | ✅ 已确认纳入 MVP |
| PvE 波次 + Boss | ❌ 移出 MVP，第二阶段交付 |
| 音效 | ✅（开源素材） |
| 音乐 | ⬜ 待定 |

**为什么团队战移出 MVP**：MVP 的目标是验证"稀疏弹道 + 走位对枪"这套核心玩法是否好玩，而这件事用混战就能完全验证。团队战带来的增量远不止"分组"：单局胜负判定、BO 赛制、共享视野、快捷信号、观战、复活次数管理、团队战掉线处理，加起来接近混战本身的工作量。在核心手感尚未验证前投入这些，风险大于收益。

### 12.2 后续更新路线（初步）

| 阶段 | 内容 |
|---|---|
| **1.1** | **PvP 团队战**（含单局胜负判定、BO 赛制、共享视野、快捷信号、团队战掉线处理）、**观战**（跟随队友 + 切换队友） |
| 第二阶段 | PvE 波次 + 首个 Boss + **PvE 局内成长**（三者作为一个整体交付）、更多道具类型 |
| 第三阶段 | 新角色、新地图 |
| 第四阶段 | 手机触屏适配、观战自由视角 |

**关于第二阶段的说明**：局内成长从第三阶段上移到第二阶段与 PvE 一同交付。原因是 PvE 的波次强度递增必须靠局内成长来承接，把成长割到后一阶段，等于先交付一个打不过的 PvE，没有验证价值。

### 12.3 明确不做（Out of Scope）❌

- 账号注册、登录、用户资料系统
- 排位赛、天梯、段位
- 商城、内购、广告
- 公开匹配大厅、陌生人随机匹配
- 反作弊系统
- 社交系统（好友、聊天室、公会）
- 排行榜（❌ 已确认不做，结算面板的本局排名足够，群内比成绩靠截图）
- 新手引导（❌ 不做，上手引导由单人练习场承担）
- 单人剧情模式

## 附录 A：道具清单

> 设计原则：TTK 目标是 5–10 秒，另加护盾耐久，实际击杀时长 8–13 秒（见 2.3.2）。**输出向增益最敏感**，容易破坏对射节奏，首版保持克制。
> 所有持续时间与数值均为**暂定值**，见 0.3 第 4 条。

### A.1 首版道具（8 种）✅

| # | 道具 | 效果 | 持续时间 | 备注 |
|---|---|---|---|---|
| 1 | 治疗包 | 立即回复一定比例的 HP | 瞬时 | 不回复护盾 |
| 2 | 护盾发生器 | **一次性补盾**：抬高护盾上限并强制进入回复状态，回满或被打断即结束 | 无固定时长，见 A.1.1 | 见下方时间线 |

| 5 | 射速强化 | 攻击间隔缩短 | 8–10 秒 | 同上 |

#### A.1.1 护盾发生器：时间线（方案 A · 一次性补盾）✅

原定义"获得独立的可吸收伤害护盾"与"防御本身就是护盾"重复，现改为**一次性补盾**。

| 阶段 | 发生什么 |
|---|---|
| T0 拾取瞬间 | 护盾上限临时提高一档；进入"强制回复"状态 |
| T0 之后 | 每秒回复护盾，**不要求脱战**（这是它区别于自然回复的核心价值） |
| 结束条件 ① | **回满**：护盾到达新上限 → 效果结束 |
| 结束条件 ② | **受到任何伤害**：回复立即中断 → 效果结束 |
| 结束瞬间 | 护盾上限回落；若当前护盾值高于回落后的上限，**截断到新上限** |

**关键点**：

- 效果**没有固定持续时间**，只有"回满"和"被打断"两种结束方式
- 被打断后不会自动续回；想继续回复需按 2.3.4 的常规规则脱战 5 秒
- 上限回落后若护盾被截断，多出来的部分被收回——这是刻意的，避免它变成永久增益

⬜ 待定：上限提高的幅度（💡 建议用固定值而非百分比，便于控制）。

#### A.1.2 护盾发生器与防御强化的区别

| 道具 | 作用 | 定位 |
|---|---|---|
| 护盾发生器 | 抬高上限 + 强制回复 | **补盾**：交战中快速回一口 |
| 防御强化 | 护盾可吸收值翻倍 | **省盾**：让现有护盾更耐用 |

两者可以叠加，叠加时护盾极难被打破。⬜ 待定：是否需要限制同时生效（💡 建议允许，稀有组合本身就是道具系统的乐趣）。

#### A.1.3 隐身：视觉与信息规则 ✅

隐身不是"消失"，而是**降级为难以察觉**：

| 通道 | 隐身时的表现 |
|---|---|
| 角色本体 | 半透明，仍可见轮廓 |
| **敌方红色描边** | ⭐ **移除**，与本体一起失去高亮 |
| 自己的弹幕描边 | ⭐ **同样移除** |
| 小地图标记 | ⭐ **移除** |
| 视线范围内的正常渲染 | 保留——仍能被看见，只是不显眼 |

**破隐条件**：**开火** 或 **受到伤害**，任一条件触发即立即破隐。

破隐瞬间要求：

- 红色描边**立刻恢复**
- 小地图标记**立刻恢复**
- 有明确的视觉提示（如一圈扩散光效），让隐身者知道自己已经暴露

⬜ 待定：隐身期间是否降低移速（作为强效果的代价）。

**设计意图**：隐身不是"无敌"，而是"从信息层消失"。它配合稀疏弹道特别有效——对手失去描边和小地图标记后，只能靠肉眼在背景里找那个半透明的身影。

### A.3 防御强化：已定案 ✅

「防御强化」原效果为"减伤"，在防御改为护盾制后失效。经讨论，采用**方案②：护盾硬化**。

| 项目 | 内容 |
|---|---|
| 效果 | 增益期间，**1 点护盾可吸收 2 点伤害**（护盾可吸收值翻倍） |
| 表现 | 护盾条外观变化（镶边/发亮），受击时扣条速度可明显看出变慢 |
| 持续时间 | 8–10 秒（暂定） |
| 实现要点 | 在伤害结算时对"护盾可吸收量"乘一个倍率，不改动伤害公式本身 |
| 与护盾发生器区分 | 护盾发生器是「抬高上限 + 强制回复」，防御强化是「让现有护盾更耐用」 |
| 边界 | 溢出伤害按**原始伤害**扣除 HP，不再折半；护盾已破时不产生任何效果 |

#### 溢出伤害的结算规则 ✅

"护盾扣除量减半"不能按字面简单实现，否则会出现反直觉的结果。正确做法是把护盾的**吸收能力**翻倍：

```
硬化生效期间，单次受击：
  可吸收量 = 当前护盾值 × 2

  if 伤害 ≤ 可吸收量:
      护盾 -= 伤害 / 2       // HP 不扣
  else:
      护盾 = 0
      HP -= 伤害 - 可吸收量   // 溢出按原始伤害扣，不再折半
```

**举例**：护盾剩 5，挨一发 20 点伤害。

| 情况 | 结果 |
|---|---|
| 无增益 | 护盾清空，HP 扣 15 |
| 硬化生效 | 可吸收量 = 10，护盾清空，HP 扣 10 |

硬化后少损失 5 点 HP，是纯收益。

**为什么不能只写"护盾扣除量减半"**：若照字面执行，护盾 5 挨 20 伤害会变成"扣 2.5 护盾、17.5 打 HP"——护盾没破，血反而掉得更多，玩家会认为这个道具是负面效果。

注：道具名称暂沿用「防御强化」，若要改名为「护盾硬化」告知即可。

### A.4 道具系统的实现约束（回顾 6.4）

新增道具不得改动战斗主逻辑，因此效果需抽象为可组合的原子效果。当前机制需要的原子效果至少有：

- 修改属性倍率（移速、射速、伤害）
- 立即回复 HP / 立即回复护盾
- 临时修改护盾上限
- 强制进入/中断护盾回复状态
- 修改符卡冷却
- 修改小地图可见性（隐身）
- 订阅事件并触发反应（受击时、击杀时）
