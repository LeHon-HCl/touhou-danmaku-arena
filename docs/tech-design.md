## 1. 需求给技术带来的硬约束

以下来自需求文档，是选型的边界条件，不满足即淘汰：

| # | 约束 | 来源 | 对选型的影响 |
|---|---|---|---|
| 1 | 浏览器端运行（Chrome / Edge） | 需求 9.1 | 排除原生引擎，或需 WebGL/WASM 导出 |
| 2 | 公网部署，玩家异地 | 需求 10.1 | 必须有服务端，不能 P2P 直连 |
| 3 | 服务端裁定命中、伤害、死亡、拾取、符卡、结算 | 需求 10.2 | 服务端必须有完整战斗逻辑，不能只做转发 |
| 4 | RTT 100ms 内手感不明显劣化 | 需求 10.1 | 需客户端预测（已定：**仅预测自身移动**），并保留回溯接口 |
| 5 | 单房间 2–8 人，同时 1–3 个房间 | 需求 10.1 | 规模很小，无需分布式架构 |
| 6 | 60 FPS | 需求 9.1 | 渲染性能要求中等 |
| 7 | 数值以服务端为真源，客户端内置默认值 | 需求 10.5 | 需要配置加载与版本机制 |
| 8 | 完整 2D 定位音效 | 需求 8.2 | 需要 Web Audio API 级别的声道控制 |
| 9 | 离线练习场（不连服务器） | 需求 4.5 | 客户端必须能脱离服务端独立运行完整战斗逻辑 |
| 10 | 像素风 + 镜头跟随 + 大地图 + 视线遮挡 | 需求 5.1 / 2.4 | 需要 tile 渲染与视野裁剪能力 |
| 11 | 无收入，服务器成本需可控 | 需求 10.3 | 排除按量计费高昂的托管方案 |
| 12 | 手机触屏仅预留，首版不做 | 需求 9.2 | 输入层需可抽象，但不是选型重点 |

**第 9 条容易被忽视但很关键**：练习场要求"不连服务器也能完整跑起来"，意味着战斗逻辑不能写死在服务端，必须是**客户端与服务端共享的一套逻辑**。这直接否决了"N 个服务端框架的推荐写法"（很多框架默认逻辑只跑在服务端）。

## 2. 已确定的架构决策（ADR）

> 架构决策记录（Architecture Decision Record）：记录"决定了什么、为什么"，防止后来的人反复推翻。

| # | 决策 | 理由 | 状态 |
|---|---|---|---|
| ADR-1 | **服务端权威**：命中、伤害、死亡、拾取、符卡、结算全部由服务端判定 | 公网环境下客户端权威既产生作弊空间，也会造成"我打中了但对方不掉血"的体验撕裂 | ✅ 需求 10.2 |
| ADR-2 | **数值混合下发**：客户端内置默认配置，联机时以服务端下发为准 | 既要离线练习场能跑，又要改平衡不用发版 | ✅ 需求 10.5 |
| ADR-3 | **不做账号体系**，仅昵称 | 内部娱乐，无持久化需求 | ✅ 需求 7.6 |
| ADR-4 | **不做反作弊系统** | 服务端权威已自然屏蔽大部分作弊，内部娱乐无需额外投入 | ✅ 需求 10.6 |
| ADR-5 | **Web 端做版本更新靠刷新**，不做补丁系统 | 浏览器天然行为 | ✅ 需求 10.5 |
| ADR-6 | **2D 定位音效用 Web Audio API** | 需要声道偏移与距离衰减，HTML5 Audio 标签做不到 | ✅ 需求 8.2 |
| ADR-7 | **网络同步采用状态同步（服务端权威）** | 帧同步要求严格确定性与全员锁步，浏览器浮点/帧率/JS 引擎差异无法保证，且掉一人全房卡住；客户端权威违反 ADR-1。只剩状态同步可行 | ✅ |
| ADR-8 | **客户端只预测自身移动**，子弹/他人位置/伤害均以服务端为准 | 稀疏弹道开火频率低，约 100ms 出弹延迟不刺眼；预测子弹需额外处理"服务端拒绝这批子弹"，复杂度不划算 | ✅ 需求 10.2.2 |
| ADR-9 | **命中判定不做延迟补偿回溯**，但保留位置历史与回溯接口 | 飞行投射物把延迟误差并入预判误差、TTK 长使单发误差代价仅约 1/15、回溯须连视线一起回溯否则会打中看不见的人。留接口以便实测后低成本升级 | ✅ 需求 10.2.1 |
| ADR-10 | **断线重连 = 保留席位 + 完整快照恢复**，复用中途加入的快照链路 | 混战允许中途加入，服务端本来就要能生成完整快照，重连复用同一条路，边际成本低 | ✅ 需求 7.4 |
| ADR-11 | **客户端 = Phaser 4**，且**只用于渲染 / 输入 / 音频 / 资源加载**，不承担任何游戏逻辑 | 本项目最可能失败的环节是"内容做不完"而非"渲染写不出来"；Tilemap、相机、图集动画、输入、资源加载、滤镜六项体力活可省约 600–800 行基建 | ✅ |
| ADR-12 | **服务端 = Node + 原生 `ws`**，自研薄房间层（约 500–800 行） | 已定的同步模型刻意做得很简单（30Hz 全量快照、只预测移动、不回溯），而 Colyseus 0.18 的强项恰是预测/校正/回溯这层复杂 netcode，用了等于为用不上的能力付框架税；且其预测 API 仅发布约两个月，出问题时资料少 | ✅ |
| ADR-13 | **`shared/` 是唯一世界状态**，语言统一 TypeScript，客户端/服务端/练习场跑同一份逻辑 | 需求约束 9 要求离线练习场脱离服务端运行，逻辑写两份必然不一致（风险 R1）；TS 的类型检查能在保存时拦下跨端字段名错误 | ✅ 需求 4.5 / 10.2 |

## 3. 客户端技术 ✅（已定案：Phaser 4）

### 3.1 定案 ✅

**Phaser 4（当前稳定版 4.2.1），仅用于渲染、输入、音频、资源加载。**

> 版本状态在 2026-11 核实：Phaser 4 系列已稳定在 4.2.x；Phaser 3 停在 3.90，官方已不再更新。

**选它的理由不是性能，而是"省基建"**：

| 本项目需要的能力 | Phaser 4 是否现成 |
|---|---|
| Tilemap 渲染 + 视口裁剪（大地图 + 镜头跟随，只会画屏幕内的格子） | ✅ |
| 图集与逐帧动画（待机/移动/射击/受击/阵亡） | ✅ |
| 相机（跟随、边界限制、缩放） | ✅ |
| 输入（键盘状态、鼠标坐标 → 世界坐标） | ✅ |
| 资源加载与进度条 | ✅ |
| 发光描边（敌方红色荧光，需求 2.4） | ✅ v4 的 Filters 系统 |

自己写这六项约需 600–800 行，而且要反复调试。这个项目的失败风险集中在"美术与内容做不完"（风险 R5），不在"渲染写不出来"，所以这 600 行应该省下来。

补充事实：本渲染量级（低分辨率像素图、8 人、约 30 发子弹）用 Canvas 2D 都绰绰有余，**性能不是本次选择的考虑因素**。

### 3.2 一个必须提前知道的坑：Phaser 4 已废弃的 API

网上绝大多数 Phaser 教程基于 v3。v4 保留了大部分 API，但以下几处会直接踩到：

| v3 写法 | v4 写法 | 备注 |
|---|---|---|
| `sprite.preFX.addGlow()` | `sprite.filters.internal.addGlow()`（需先 `enableFilters()`） | 本项目要用它做敌方描边 |
| `Phaser.AUTO` 会自动退回 Canvas | Canvas 渲染器已废弃，v4 实际走 WebGL | 极老的设备/浏览器可能不兼容 |
| 后处理管线 `postFX` | 统一并入 Filters | |

**应对**：遇到报错先判断"这段是不是 v3 教程"，v4 官方文档与 TypeScript 类型定义（`node_modules/phaser/types`）是最终依据。

### 3.3 明确不做的事 ❌

- **不使用 Phaser 的物理系统**（Arcade Physics / Matter）。物理与碰撞必须在 `shared/` 里自己实现，否则服务端与练习场跑不出一样的结果（ADR-13）
- **不使用 Phaser 的场景状态管理来持有对局数据**。世界状态只存在于 `shared/`，Phaser 只读取它并画出来

### 3.4 被淘汰的方案与原因

| 方案 | 淘汰原因 |
|---|---|
| Phaser 3 | 已停止更新（3.90 为终版），新项目无理由上上一代 |
| PixiJS 8 | 纯渲染引擎，Tilemap / 相机 / 输入都要自己搭薄壳。渲染更快，但本项目不缺渲染性能 |
| 自研 Canvas 2D | 零依赖、完全可控，但需自写 600–800 行基建，且踩坑无人可问 |
| Unity WebGL | 包体大、首屏慢，与"服务器权威 + 轻量 Web"的定位不匹配 |
| Godot 4 Web | 导出与 2D 性能不错，但 Web 多人生态资料少，且与 `shared/` 纯 TS 逻辑层的协作不自然 |

## 4. 网络同步模型 ✅（已定案）

这是本项目技术难度最高的一块，也是最容易踩坑的地方。先解释三个常见模型，再给出定案。

### 4.1 模型说明

| 模型 | 做法 | 适用 | 本项目适配度 |
|---|---|---|---|
| **状态同步（服务端权威）** | 客户端把输入发给服务端，服务端跑逻辑，把结果状态广播回来；客户端做本地预测来掩盖延迟 | 大多数现代多人游戏 | ⭐ 最契合 |
| **帧同步（Lockstep）** | 所有客户端跑同一套确定性逻辑，只同步输入指令 | RTS、格斗游戏 | 不适合：需要严格确定性，浏览器浮点与帧率难以保证，且要"全员等最慢的人" |
| **客户端权威** | 客户端自己算命中，上报服务端 | 休闲游戏 | ❌ 违反 ADR-1 |

### 4.2 状态同步的三个关键概念

1. **客户端预测（Client-side Prediction）**：本地按键后，不等服务端回包，先自己算出这个操作应该产生什么结果，让操作**零延迟**呈现。预测范围可大可小——最少只预测移动，也可以连攻击一起预测。
2. **服务端校正（Reconciliation）**：服务端的权威状态回来后，如果和本地预测不一致，平滑地把本地状态纠正过去。做不好会表现为"拉回"（rubber-banding）。
3. **延迟补偿（Lag Compensation）**：射击时，服务端回溯到"玩家开火那一刻"的世界状态再判定命中，否则高延迟玩家会"明明瞄中了却打空"。

💡 **对本项目的两个观察**（定案见 4.3）：
- 稀疏弹道 + 8–13 秒实际击杀时长，对判定的宽容度**比高节奏 FPS 高得多**
- 但**移动**必须有客户端预测，否则操作会有明显粘滞感

### 4.3 定案：四项决策 ✅

| 项 | 结论 | 详见 |
|---|---|---|
| 同步模型 | **状态同步 + 服务端权威**。客户端上报输入，服务端跑逻辑并广播状态 | ADR-7 |
| 客户端预测 | **只预测自身移动**；子弹、其他玩家位置、伤害与死亡均为服务端权威 | ADR-8 / 需求 10.2.2 |
| 命中判定 | **按服务端当前世界状态判定，不做回溯**；但照存最近约 200ms 位置历史并留回溯接口 | ADR-9 / 需求 10.2.1 |
| 断线重连 | **保留席位 60 秒 + 完整快照恢复**，复用中途加入的快照链路 | ADR-10 / 需求 7.4 |

**为什么不做延迟补偿**（这是最容易被质疑的一条，理由要留档）：

1. 偏差只发生在**横向移动**的目标上。目标迎面来或背身去时，位置误差只改变命中时刻，不改变是否命中
2. 本项目用飞行投射物，玩家本来就在打提前量，延迟误差被并入预判误差，玩家无法区分、会自然补偿
3. TTK 8–13 秒需命中十几次，单发失误代价约 1/15
4. 回溯必须连**视线遮挡**一起回溯，否则会"打中一个当时看不见的人"；两个都回溯则成本与 bug 面翻倍，且"进掩体还被打死"会变频繁

**升级路径**：位置历史与回溯接口在 MVP 就位。若实测确认"高延迟玩家明显打不中"，打开开关即可切回溯判定，无需重构。

### 4.4 传输层与频率 ✅（参数为暂定值）

| 参数 | 取值 | 理由 |
|---|---|---|
| 传输层 | **WebSocket** | 数据量小、频率低，TCP 队头阻塞在 30Hz 小包场景影响有限；WebRTC 需额外做 STUN/TURN 与信令，复杂度远超收益 |
| 服务端逻辑帧率 | **30 Hz**（每 33ms） | 弹速 600 px/s 时 33ms 只走 20px，小于角色直径，不会出现"子弹穿过人没判定" |
| 状态广播频率 | **30 Hz，全量快照** | 见下方带宽估算；这个量级做增量同步没有收益，全量反而不会出错 |
| 远端渲染 | **两快照间插值** | 代价是他人画面晚约 33ms，换来平滑不抖 |

### 4.5 同步频率与带宽估算 💡

按 8 人、30Hz、全量快照粗算（原型阶段实测确认）：

| 项目 | 单帧大小 | 说明 |
|---|---|---|
| 8 名玩家状态 | ≈ 130 字节 | 每人约 16 字节：id、坐标、速度、朝向、HP、护盾、状态位 |
| 约 30 发活跃子弹 | ≈ 300 字节 | 每发约 10 字节：id、坐标、速度、归属 |
| 包头与时间戳 | ≈ 30 字节 | |
| **合计** | **≈ 460 字节/帧** | |

- 每客户端下行：460 B × 30 Hz ≈ **13.8 KB/s**
- 服务端上行（8 人）：≈ **110 KB/s**
- 单房间带宽占用在 1 Mbps 以内，最低配云服务器绰绰有余

⬜ 待原型阶段实测确认实际包大小与发包策略。

## 5. 服务端技术 ✅（已定案：Node + ws）

### 5.1 定案 ✅

**Node.js + TypeScript + 原生 `ws`，自研一层薄房间管理。**

服务端要做的事比想象中少——只有四件：**房间管理、30Hz tick、快照广播、重连席位**。预期 1–3 个房间、24 人上限，没有任何扩展性压力。

| 模块 | 职责 | 预估规模 |
|---|---|---|
| WebSocket 服务 | 连接、消息收发、心跳 | 约 100 行 |
| 房间管理 | 创建/加入/离开、房间号、房主转移 | 约 200 行 |
| 对局循环 | 30Hz tick，调用 `shared/step.ts` 推进世界 | 约 150 行 |
| 快照广播 | 序列化世界状态、按房间广播 | 约 100 行 |
| 重连席位 | 60 秒席位保留、快照恢复、复用中途加入链路 | 约 150 行 |

合计约 **500–800 行**，规模不会失控。

### 5.2 为什么不用 Colyseus（这是本轮最反直觉的一条）

Colyseus 0.18（2026 年 8 月）刚加入了**内置的客户端预测、服务端校正与回溯判定**——正是我们在第 4 章决定手写的那套东西。看起来"免费的午餐"，但它反而成了不选它的理由：

1. **它的强项恰好是我们不要的**。已定的同步模型刻意做得很简单（30Hz 全量快照、只预测自身移动、不做回溯）。用 Colyseus 等于为用不上的能力付框架税
2. **会引入第二份世界状态**。世界状态只有一份（`shared/` 里的纯数据），Colyseus 要求用 Schema 装饰器再声明一遍，等于同一份数据维护两处，正是风险 R1 的温床
3. **那套预测 API 只有约两个月**。出问题时社区资料几乎为零，排查成本高
4. **项目负责人要求能大致理解自己用的技术栈**。自己写的 500 行每一行都读得懂

**次选仍是 Colyseus**：如果将来判断变成"宁可多学一个框架也不想自己碰房间与重连"，它确实能省掉最容易写错的那部分——尤其是重连。

### 5.3 为什么不用 Socket.io

Socket.io 提供通信层 + 广播分组 + 传输层自动重连，是 ws 与 Colyseus 之间的折中。但本项目：

- 房间只有 1–3 个，广播分组没有价值（一间房一个分组）
- 它的通信协议比裸 WebSocket 多一层封装与开销，而我们自己控制协议格式反而更短
- 传输层自动重连对我们无用——我们做的是**席位级重连**（回到原对局并恢复完整状态），而不是 Socket.io 那种"重新连上"级别的重连

### 5.4 需回答的问题 ✅

| 问题 | 结论 |
|---|---|
| 房间生命周期怎么管 | **纯内存**。进程重启房间丢失可接受——重连本就是"刷新页面重进"级别的容错，不追求进程级容灾 |
| 是否需要持久化 | 不持久化对局；**数值配置落盘**（由服务端下发，见需求 10.5）；对局日志写文件（需求 10.7） |
| 单进程能否承载全部房间 | 能。30Hz × 3 房间 = 每秒 90 次 tick，压力可忽略 |

## 7. 工程与配置

### 7.1 定案 ✅

| 项目 | 结论 | 理由 |
|---|---|---|
| 语言 | **TypeScript** | `shared/` 里同一份战斗逻辑要被客户端、服务端、练习场三处调用。纯 JS 下一个字段名打错，表现为"服务端打人没伤害"，要到联机测试才发现；TS 在保存文件时就拦下 |
| 客户端构建 | **Vite** | 开发服务器、TS 编译、热更新、打包全包；配置文件只有一个 `tsconfig.json`，无 Webpack / Babel |
| 服务端运行 | **tsx** | 直接运行 `.ts`，不用先编译；启动命令 `tsx server/src/index.ts` |
| 包管理 | npm（随 Node 附带） | 无需额外引入 pnpm/yarn |

**工具链总负担**：需要新学的只有 Vite 与 tsx 两个东西，都是一条命令的事。

- 建客户端：`npm create vite@latest client -- --template vanilla-ts`
- 跑服务端：`npm install -D tsx`，然后 `npx tsx server/src/index.ts`

没写引擎、没配 loader、没写构建脚本——这是 2026 年做这件事最简的方式。

⚠️ **真实代价**：写代码时会经常看到红色波浪线。这是好事（它在替你查跨端字段错配），但前两周写代码会慢一些。

### 7.2 配置表与资源打包 ✅

#### 7.2.1 配置表的管道

配置的**编写规范**（TS 模块、单位、注释、命名、版本号、校验）全部在 [dev-conventions.md](./dev-conventions.md) 第 6 章，本节只说**它怎么变成运行时数据**：

```
shared/config/*.ts          ← 人在这里改数值（改完当场有类型检查）
        │  npm run build:config
        ▼
config/game-config.json     ← 构建产物，带 version（内容 hash，前 8 位）
        │  服务端启动时读入（只校验：存在 / 可解析 / 有 version）
        ▼
server 内存中的权威数值
        │  玩家进房时整包下发
        ▼
client 用它覆盖内置默认值   ← 内置值只服务离线练习场（需求 10.5）
```

| 环节 | 结论 | 理由 |
|---|---|---|
| 源格式 | **TS 模块** | 编译期拦字段名与类型错误；JSON 写错要到运行时才炸 |
| 中间产物 | **单个 JSON 文件** | 服务端与客户端都只认一种格式；改完重启进程即生效（dev-conventions 6.6.4） |
| 放在哪 | 仓库根的 `config/`，**入库** | 让服务端拉下代码就能直接启动，不依赖在生产机上装构建链 |
| 谁读它 | 只有服务端读文件；客户端从网络拿 | 客户端不去读磁盘，避免"前端有旧文件"这类问题 |
| 版本号用途 | 只进日志，不拦截 | 详见 dev-conventions 6.6.2 |

**这条管道的代价要说清楚**：多一个 `build:config` 步骤，改完数值忘了跑它，服务端就会读到旧 JSON。所以 `npm run dev` 与服务端启动脚本里都**要串上这一步**，让人无法漏掉。

#### 7.2.2 资源打包：MVP 不打包

| 项目 | 结论 |
|---|---|
| 图集（atlas） | ❌ **MVP 不打包**，单张 PNG 直载 |
| 例外 | 地图 **tileset 必须是一张索引图**（Phaser tilemap 按格切分，这是硬性要求） |
| 加载时机 | **按场景分包**，不一次性全载 |
| 工具 | 不引 TexturePacker / free-tex-packer |
| 首屏体积预算 | 💡 全部素材 ≤ 1 MB（48×48 PNG 单张约 2–5 KB；主要体积在 tileset 与音效） |

- 选人界面：只加载 `char/`
- 对局 / 练习场：`char/` + `bullet/` + `item/` + `map/` + `sfx/`

**为什么不做图集**：素材约 25 个文件，HTTP/2 下并发请求开销可忽略；图集换来的是"改一张图要重新打包"和"图集没更新"这类排查成本。**数量少的时候打包是纯成本。**

**升级路径**：Phaser 里 `load.atlas()` 与 `load.image()` 只差一行，渲染侧引用的是帧名而非路径，所以真需要打包时换加载方式即可。命名规则见 dev-conventions 第 7 章。

#### 7.2.3 其余工程项

| 项目 | 状态 | 说明 |
|---|---|---|
| 状态管理（前端） | ✅ 不需要额外库 | 世界状态在 `shared/`，渲染层每帧读它；没有需要"状态管理"的前端状态 |
| 代码风格与 Git 流程 | → dev-conventions.md | 不属于本文档 |

## 8. 目录结构与模块划分 ✅

### 8.1 目录结构

```
PixelGameProgram/
├── docs/                       # 四份文档
├── shared/                     # ⭐ 纯 TS，零框架依赖，客户端/服务端/练习场共用
│   ├── world.ts                # 世界状态的数据结构（玩家、子弹、道具、地图状态）
│   ├── step.ts                 # 固定步长推进：输入 → 移动 → 碰撞 → 命中 → 伤害 → 复活
│   ├── protocol.ts             # 通信消息类型（输入上行、快照下行）
│   ├── sim/                    # 弹道、命中判定、护盾与伤害、道具效果处理器
│   └── config/                 # 数值配置的 TS 源（改数值改这里）+ 类型定义
├── assets/                     # 素材成品，按类型分目录（命名规则见 dev-conventions 第 7 章）
│   ├── char/  bullet/  item/  map/  sfx/
├── config/
│   └── game-config.json        # ⚠️ 构建产物，由 build:config 从 shared/config 生成，入库
├── scripts/
│   └── build-config.ts         # shared/config → config/game-config.json（内含 version hash）
├── client/                     # Phaser 4 + Vite
│   └── src/
│       ├── main.ts             # 启动、场景注册
│       ├── render/             # 世界状态 → 画面（只读，绝不写 world）
│       ├── net/                # WebSocket、快照接收、自身移动预测与校正
│       ├── input/              # 键鼠采集 → 抽象输入指令
│       ├── audio/              # Web Audio API 定位音效（ADR-6）
│       └── practice/           # 离线练习场：本地跑 shared/step.ts，不连服务端
├── server/                     # Node + ws
│   └── src/
│       ├── index.ts            # WebSocket 服务、连接与心跳
│       ├── room.ts             # 房间：30Hz tick、快照广播、重连席位
│       ├── rooms.ts            # 房间注册表、房间号、房主转移
│       └── log.ts              # 对局日志（需求 10.7）
└── package.json                # 单仓库 workspace：tools 统一放在根
```

**两处容易搞错的边界**：

| 目录 | 谁写 | 谁读 |
|---|---|---|
| `shared/config/` | 人改数值（TS 源） | 三端都 import 它取**类型**；客户端另外取**内置默认值**（离线练习场与下发失败兜底） |
| `config/game-config.json` | `build:config` 脚本生成 | **只有服务端读**，作为权威数值来源。客户端从网络拿，不去读磁盘 |

服务端启动脚本写成 `npm run build:config && tsx server/src/index.ts`，把生成步骤串进去，就不存在"忘了跑构建、读到旧 JSON"的窗口。

`assets/` 只在 `client/` 里被引用（服务端不需要任何素材）。

### 8.2 一条硬纪律（比任何代码规范都重要）

> **`shared/` 里不允许出现 `import Phaser`，也不允许出现 `import ws` / `node:*` / `fs` / 任何浏览器 DOM API。**

理由：`shared/` 要被三种运行环境同时执行——浏览器（联机客户端）、Node（服务端）、浏览器（离线练习场）。只要引入任何一端的专属 API，另外两端就崩。一旦破了这条，练习场先跑不起来，接着服务端跑不起来，最后只能写两份逻辑，正是风险 R1/R6 的起点。

**把它当作 review 时的第一条检查项。** 可以在 `shared/tsconfig.json` 里把 `lib` 设为纯 `ES2022`（不含 `DOM`），让编辑器直接报错，比靠人记更可靠。

### 8.3 三种运行模式共用一条推进函数

| 运行模式 | 谁调用 `step.ts` | 逻辑帧率 | 状态来源 |
|---|---|---|---|
| 联机对局（服务端） | `server/room.ts` | 30 Hz | 自己推出来的，是权威 |
| 联机对局（客户端） | **不调用**，只接收快照 | — | 服务端广播 |
| 离线练习场 | `client/practice/` | 30 Hz（本地） | 自己推出来的 |

也就是说 **`step.ts` 只有一个实现，两条调用路径**。客户端的职责只有"预测自己的移动 + 把世界画出来"，它不推进世界。

这条划分是 ADR-8（只预测自身移动）在工程上的直接体现：客户端不跑完整 world step，所以不存在"客户端算出一种结果、服务端算出另一种"的空间。

## 9. 技术风险清单

| # | 风险 | 影响 | 缓解思路 |
|---|---|---|---|
| R1 | 客户端与服务端逻辑不一致，出现"显示打中但没掉血" | 体验崩坏 | 共享同一份逻辑代码；数值单一来源（ADR-2） |
| R2 | 没有同步经验，预测/校正做不好导致"拉回"明显 | 手感差 | MVP 先做最简单的预测，宁可牺牲精度也要稳 |
| R3 | 视线遮挡 + 小地图的"最后已知位置"实现复杂 | 工期 | 先做全图可见版本验证玩法，遮挡后加 |
| R4 | 服务器成本超出预期 | 项目中止 | 先本地局域网验证，再上公网 |
| R5 | 像素风素材量大，拖慢进度 | 工期 | 先用几何占位图跑通，美术后置 |
| R6 | 离线练习场与服务端逻辑重复实现 | 维护成本翻倍 | 强制共享逻辑层，不允许写两份 |
| R7 | **Phaser v3 教程与 v4 API 混杂**，照抄报错、排查耗时 | 工期 | 第 3.2 节列出已废弃 API；以 v4 官方文档与本地类型定义为最终依据 |
| R8 | 团队工程经验有限，工具链与项目配置本身耗时 | 工期 | 只引入 Vite + tsx 两个工具，配置文件尽量少；第一个里程碑只做"能跑起来的最小联机 demo" |
| R9 | **Colyseus 的诱惑**：中途发现房间/重连不好写而换框架 | 返工 | ADR-12 已留档理由；若确需更换，重连是唯一值得单独买的功能，其余自研部分可平移 |
